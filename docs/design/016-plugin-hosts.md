# 016: plugin hosts, a pure core and one API

The four format hosts (`tutti-vst2-host`, `tutti-vst3-host`,
`tutti-clap-host`, `tutti-au-host`) each decide the same lifecycle questions in
their own FFI-calling code, and expose four API shapes for one set of
operations. This design moves the decisions into a pure core in
`tutti-plugin-types`, gives the formats one set of typestate traits whose
activation splits a plugin into a realtime Processor and a main-thread
Controller, and leaves each host crate an interpreter of effects over its FFI.

What a loaded plugin *declares* (units, voices, tail, layouts, presets) is
typed in [023](023-plugin-capabilities.md).

## Summary

- **A pure core.** `step(State, Event) -> (State, Effects)` decides activation,
  restart, rescan and latency or tail re-reads for every format. It has no FFI
  and no plugin, and property tests run it over event sequences (§2.1).
- **Split handles, static dispatch.** `Loaded` is implemented on each format's
  loaded type. `Loaded::activate(self, Prepare)` returns a `Processor`, which only
  the realtime thread holds and which only renders, and a `Controller`, which the
  main thread holds and which carries the control surface. `Loaded::deactivate`
  rejoins the halves. The traits are deliberately not object-safe (§2.2).
- **One driver.** `Lifecycle<L: Loaded>` holds a plugin in whichever state it is in,
  the Processor lent to the realtime thread or not, and interprets `Effect`s
  against it. It is written once and replaces the
  restart, rescan and reactivate code in the four server loaders (§2.3).
- **A closed set, no `dyn`.** `AnyPlugin` is an enum of the four `Lifecycle`s,
  generated by one macro. A user of one format uses `Lifecycle<ClapLoaded>` directly
  (§2.4).
- **The state in the type.** `Plugin<Inactive>` and `Plugin<Active>`: port
  configuration only on the first, latency and tail only on the second, the
  Controller holding the second, no `active` flags (§2.11).
- **One vocabulary** (`ParamId`, `Normalized`, `SampleRate`, `Samples`,
  `activate`/`deactivate`, std-idiomatic names) (§2.5).
- **A thin shell.** Plugin-initiated calls become `Event`s through one atomic
  word, consumed on the main thread. The Processor/Controller split is the plugin
  server's main and realtime thread split: the main thread runs `step`, `apply` and
  the Controller, the realtime thread owns the Processor and calls `process`
  (§2.6).
- **The server and the client follow.** `Session` is generic over what it hosts
  and is tested against a `FakePlugin`. The client protocol becomes a transition
  function (§2.7). Discovery is `FileFacts` in and `classify` out (§2.8).
- **Safety is folded in.** Both halves reach one plugin instance; the spec rule
  that makes that legal is stated per format. VST2 has none, so it follows the
  host convention, and a per-plugin quirk serializes state loads by swapping in
  a shadow instance (§2.2, §2.10). A safe `Editor` API, `Send`/`Sync` argued
  per type, a safe AU surface, panics caught in callbacks, no raw FFI in public
  modules (§2.9).

Everything named in §2 is new unless §3's tables name the existing item it
replaces. Types and methods that exist today are cited with their file and
line.

## 1. The problem

### 1.1 One decision, written four times

Restart and rescan servicing sits inside four FFI-calling loader methods.

- VST3: `tutti-plugin-server/src/loaders/vst3.rs:362` `poll_restart` reads the
  flag word, cycles the bus configuration when I/O or latency changed, rebuilds
  the CC mapping, and reloads the whole instance when asked. A poll with both
  `io_changed` and `reload_requested` cycles the buses and then throws the cycle
  away in the reload.
- CLAP: `loaders/clap.rs:537` `service_requests` reduces the same question to
  `ports.needs_deactivate() || restart || params.needs_deactivate() || (latency
  && was_active)`, calls `reactivate`, then compares `active` with `was_active`
  and stores the result in a latch field (`io_changed`, taken by
  `take_io_changed`, `clap.rs:648`).
- VST2: `loaders/vst2.rs:142` `poll_changes` re-reads latency, tail and pins.
- AU: `loaders/au.rs:687` `poll_changes` maps property flags to the same
  events.
- `plugin.rs:298` `poll_async_events` is a per-format `match` whose arms map
  each loader's outcome to `AsyncEvent`. "A reload subsumes the finer flags"
  (`plugin.rs:322-333`) is real logic reachable only with a loaded plugin.

Each loader also keeps a `Meta.loaded` cache of latency, tail and bus layout
(30 reads and writes under `loaders/`), refreshed differently per format: VST3 in
`poll_restart` and on reload, AU at `au.rs:698` and `:750`, VST2 at `vst2.rs:145`
and CLAP in `note_latency_change` (`clap.rs:605`). A cache refreshed by hand per
format is a stale copy waiting for the next format to forget it.

The bug class is a sequencing rule written in one loader and missed in another:
a `latency.changed` raised inside `activate` restarted the plugin again (the
`a_latency_changed_inside_activate_is_not_restarted_for` test at
`clap.rs:1723` pins the CLAP fix). The rule is format-independent, and today it
can be tested only against a real plugin built by `cargo build -p
tutti-plugin-server`.

### 1.2 Four API shapes for one set of operations

| Operation | VST2 | VST3 | CLAP | AU |
|---|---|---|---|---|
| Lifecycle types | one type, `Vst2Instance` (`instance.rs:155`) | `Vst3Loaded` / `Vst3Active<T>` | `ClapLoaded` / `ClapActive<T>` | `AuLoaded` / `AuActive`, and a façade `AuInstance` with its own `State` enum (`instance.rs:96,2245`) |
| Activate | n/a (`suspend` / `resume`, `instance.rs:441,449`) | `activate::<T>(rate, block)` | `activate::<T>()` | `initialize()` |
| Failed activate | n/a | consumes `self`, no handback | `(Self, ClapError)` | `(Option<Self>, AuError)` |
| Load | `load(&Path, f64, usize)` | `Vst3Loaded::load(&Path)`, `Vst3Active::load(&Path, f64, usize)` | `load(impl AsRef<Path>, f64, u32)` and four more loaders | `unsafe AuLoaded::new(component)` |
| Parameter read | `Option<f32>`, id `i32` | `f64`, id `u32` | `Option<f64>`, id `u32` | `Result<f32>`, id `u32` |
| Latency | `latency() -> Samples` | `read_latency_samples() -> u32` | `get_latency() -> u32` | `get_latency() -> Result<Samples>` |
| Sample rate | `f64` | `f64` | `f64` | `f64` |

`tutti-plugin-types` has capability traits (`PluginMeta`, `PluginAudio`,
`PluginParams`, `PluginState`, `PluginPresets`, `PluginEditorHost`, bundled by
`PluginInstance`; `format_host.rs`) that the *server loaders* implement, not the
hosts. The inherent surface a host user sees drifts from the traits, and
`format_host.rs`'s module doc argues against a lifecycle trait at all. That
argument rests on the server erasing the format behind `&mut dyn PluginInstance`.
With a closed set of four formats and a macro-generated enum, the erasure is not
needed (§2.4), and the typestate each format already has survives to the seam.

### 1.3 The server cannot be tested without a plugin

`Session` holds the concrete `Plugin` enum (`session.rs:97`). Rate refusal then
silence then revive (`a_refused_rate_is_silent_and_a_later_rate_revives_the_plugin`),
the f32 and f64 round trips, the state-chunk path and the parameter path all call
`load_clap(..)` (16 call sites in `session.rs`). Only the no-plugin cases run
without the plugin-server build prerequisite.

The `Reaction` loop is written twice (`server.rs:115-137`, `140-158`), and the
`AsyncEvent` to `BridgeMessage` map is inline in `Session::drain_async_events`
(`session.rs:356-371`).

### 1.4 The client protocol is socket-bound

`tutti-plugin-ipc/src/client/audio/dispatch.rs` `handle` is a
400-line function over the concrete `ControlStream`. It sends, settles `Owed`,
reads a reply with a resumable partial-frame cursor, classifies timeout against
crash, and runs a rate-change wait loop with its own `Instant::now()` deadline.
The protocol rules in it (a missed block budget costs the block, not the
connection; a late rate reply is taken off the socket before the next send) are
reached only through real local sockets (`hostile_peer_tests.rs`, 1505 lines).
`Batcher::await_output` (`host/node/batcher.rs:380`) mixes the wait policy with
the clock, and its four rules (the first miss is the last wait; a dead server
ends the wait at once; a refusal is silence at once; a reply wait never gives up)
are tested only by `real_stall_tests.rs`, against a real server.

### 1.5 Discovery reads the filesystem inside decisions

Before this change, `CatalogExt::is_blacklisted_and_unchanged` and `needs_rescan`
called `file_modification_time(path)`; `blacklist` called it and
`format_from_path`; `prune_missing` called `path.exists()`. The scanner's
`classify` was therefore a decision plus stat calls, stat-ed twice per file, and
its tests built real directories and relied on mtime moving. `JsonCatalog::load`
and the dead-man's pedal `recover` mixed read, parse, decide, rename and log.

### 1.6 Unsafe on the public surface

- `HostEditor::open_editor(&self, parent: *mut c_void, ..)` is a safe trait
  method taking a raw pointer (`host/handles/capabilities.rs:187`); impls turn it
  into a `WindowHandle` with `unsafe` on the caller's word
  (`format/vst2_in_process/control_backend.rs:207`,
  `host/ipc_client/composite.rs:275`).
- `WindowHandle::{from_raw, from_ptr, from_u64}` are `pub unsafe fn`
  (`tutti-plugin-types/src/editor.rs:20,30,42`): three constructors for one
  operation, reachable as `tutti_plugin::server::WindowHandle`.
- `tutti-au-host` has 40 `pub unsafe fn` and a public raw `AudioComponent`
  field, because `raw_unit()` hands out the pointer the listener and notify
  functions then require (`instance.rs:131,154,189,2139,2179`,
  `listener.rs:445,624,675,723`).
- `unsafe impl Send + Sync for Vst2Instance` rests on "callers serialize
  externally" (`tutti-vst2-host/src/instance.rs:190-197`) on a public type with
  `&self` methods.
- `tutti-clap-host` defines 94 `extern "C"` callbacks and one `catch_unwind`
  (`host/thread_pool.rs:252`).
- `tutti-au-host`'s `decode_packet_list_for_test` and
  `split_packet_list_for_test` are `#[doc(hidden)] pub unsafe fn`
  (`midi_out.rs:675`). `tutti-clap-host` has `pub mod host/instance/types/
  topology` and safe `pub fn as_raw()` returning FFI pointers (`lib.rs:5-8`,
  `events.rs:1162,1299`).

## 2. The design

### 2.1 The pure core, in `tutti-plugin-types`

A private module, with its items at the crate root. No FFI, no I/O, no clock.
Everything here runs on the control (main) thread; nothing runs on the audio
thread. The only effects that touch the realtime thread are `Recall` and `Lend`,
which move the Processor between the threads (§2.6).

```rust
/// What a host asks of a plugin, an effect finished, or the plugin asked.
pub enum Event {
    Op(HostOp),
    /// A plugin-initiated call, raised on any thread, delivered here.
    Request(Request),
    /// The main-thread idle pass: act on what has been requested.
    Tick,
    /// What the shell found when it interpreted the last `Effect`.
    Replied(Reply),
    /// The Processor is back from the realtime thread after a `Recall`, or, in
    /// `SwapPhase::Fading`, the outgoing Processor of a swap.
    Returned,
    /// The process hosting the plugin is gone.
    Died,
}

pub enum HostOp {
    Activate(Prepare),
    /// A new rate, block size, format or mode: deactivate and activate again.
    Reconfigure(Prepare),
    Deactivate,
    /// Apply the state staged in the shell (`Staged` names it; the bytes never
    /// enter the core). Direct on the Controller, or through a shadow (§2.10).
    LoadState(Staged),
}

/// What the plugin called on the host.
pub enum Request {
    Restart,
    /// An audio-ports rescan (CLAP), `kIoChanged` (VST3), `audioMasterIOChanged`
    /// (VST2), a stream-format property (AU).
    IoChanged,
    RescanParams(RescanScope),
    LatencyChanged,
    TailChanged,
    /// `kReloadComponent`: rebuild the instance.
    Reload,
    /// `request_callback` (CLAP): run `on_main_thread`.
    Callback,
    /// VST3 `kMidiCCAssignmentChanged` and `kNoteExpressionChanged`.
    MidiCcAssignmentChanged,
    NoteExpressionChanged,
    Timer(TimerId),
    Fd(FdId),
}

pub enum RescanScope { Values, Text, Info, All }

pub enum Effect {
    /// Splits the plugin into a Processor and a Controller.
    CallActivate(Prepare),
    /// Rejoins the halves. Needs both in hand, so `Recall` precedes it.
    CallDeactivate,
    /// Rebuild the instance from its load parameters (VST3 reload). Needs the
    /// plugin loaded, so a `Recall` and a `CallDeactivate` precede it when active.
    Rebuild,
    /// Ask the realtime thread to hand the Processor back, between blocks.
    Recall,
    /// Give the Processor to the realtime thread.
    Lend,
    /// `Loaded::load_state` on the Controller, in place (§2.10).
    ApplyLoad(Staged),
    /// Load a second instance, apply the staged state to it, activate it at the
    /// live `Prepare` (§2.10). Main thread.
    LoadShadow(Staged),
    /// Hand the shadow's Processor to the realtime thread as a swap: a `Lend`
    /// while the seat is already `Lent`. The shadow's Controller becomes the
    /// live one; the old one waits for the old Processor.
    SwapTo,
    /// The old Processor is back: `deactivate` the old pair and drop the plugin.
    Retire,
    ReadLatency,
    ReadTail,
    ReadLayout,
    ReadParams(RescanScope),
    /// Rebuild the host's MIDI controller mapping from the plugin.
    RebuildMidiMapping,
    RunMainThread,
    RunTimer(TimerId),
    ServiceFd(FdId),
    Notify(Notice),
}

pub enum Reply {
    Activated,
    Refused(PluginError),
    Deactivated,
    Rebuilt,
    Latency(Samples),
    Tail(PluginTail),
    Layout(Layout),
    /// The effect needs a state the plugin is not in (a read while loaded).
    NotActive,
    /// `Recall`: the Processor is already held.
    Returned,
    /// `Recall`: the Processor is on the realtime thread; `Event::Returned` follows.
    Lent,
    /// `LoadShadow`: the shadow is active and holds the state.
    ShadowReady,
    /// `LoadShadow`: the second instance would not load, take the state or
    /// activate. The live pair is untouched.
    ShadowFailed(PluginError),
    /// `CallDeactivate`: the plugin would not stop. Both halves are intact.
    Stuck(PluginError),
    Done,
}

/// What the host is told, in the order it happened.
pub enum Notice {
    LatencyChanged(Samples),
    TailChanged(PluginTail),
    IoChanged,
    ParamValuesChanged,
    ParamTitlesChanged,
    NoteExpressionChanged,
    Reloaded,
    Refused { rate: SampleRate, reason: PluginError },
    Stuck { reason: PluginError },
    /// A state load did not take; the plugin is as it was.
    LoadFailed { reason: PluginError },
}

/// What `activate` needs, and what a change of any field costs: a deactivate
/// and an activate.
/// Fields are private: `Prepare::new(rate, max_block) -> Option<Self>` refuses a
/// rate that is not finite and positive, and `MaxBlock` (`tutti-types`) holds at
/// least one frame. `with_format`, `with_mode` and `with_rate` change one field.
pub struct Prepare { /* rate: SampleRate, max_block: MaxBlock, format, mode */ }

pub struct State { /* stage, last Prepare, latency, tail, layout, pending requests,
                     the plan parked behind a recall, `shadow_loads`, `swap` */ }

/// Where a shadow load is. `Idle` is every state but a load in flight.
pub enum SwapPhase { Idle, Loading, Fading }

pub enum Stage { Loaded, Active, Refused { rate: SampleRate }, Poisoned }

/// Effects one `step` can emit: a bound, so a step never allocates.
pub const EFFECT_CAPACITY: usize = 14;
pub type Effects = arrayvec::ArrayVec<Effect, EFFECT_CAPACITY>;

pub fn step(state: State, event: Event) -> (State, Effects);
```

`SampleFormat` (f32 or f64) moves down from `tutti-plugin`'s protocol module
(`protocol/sample.rs:12`) to `tutti-plugin-types`; `tutti_plugin::protocol`
re-exports it, as it does the other types it adopts.
`Layout` is `BusLayout` (`loaders/clap.rs:254`: the buses and their topologies,
`PartialEq`) moved down. `RenderMode`, `Samples`, `PluginTail`, `PluginError`
and `ParamId` exist today; `SampleRate` is `tutti_types`'s, re-exported beside
`Samples`.

A transition is a split or a rejoin: `CallActivate` turns a whole plugin into two
halves, and `CallDeactivate` and `Rebuild` need the halves back together. A plan
therefore ends a deactivation with the Processor on the main thread, which is what
`Recall` buys.

The effects a step emits are executed by the shell, and each effect's result
returns as `Event::Replied`. The loop is `Lifecycle::drive` (§2.3).

**What step 1 of §7 builds.** The code block above is the whole vocabulary;
the first step builds the part that needs no state load and leaves the rest to
step 9, which adds it with its own variants: `HostOp::LoadState` and `Staged`,
`Effect::{ApplyLoad, LoadShadow, SwapTo, Retire}`,
`Reply::{ShadowReady, ShadowFailed}`, `Notice::LoadFailed`, `SwapPhase`, the
`shadow_loads` and `swap` fields and rules 11 to 14 with their properties.
Four things the block leaves open are fixed as follows.

- **A step emits up to the next effect that is waited on.** `Recall`,
  `CallDeactivate`, `Rebuild` and `CallActivate` each end a step's output; the
  rest of the plan stays in `State` and the reply to that effect continues it.
  Rules 1, 5 and 9 read "emits `Recall`, `CallDeactivate`, `CallActivate`" as the
  sequence over a `drive`, not one step's output; a plan that could not stop
  after `Replied(Lent)` would not be parkable. A reply that answers no effect in
  flight (an `Activated` with no activation, a `Returned` with no recall) is
  ignored, which is also why a refused or poisoned plugin cannot be revived by a
  stray reply.
- **`State::new(RestartRules)`.** Rule 5's "only where the format's rules say it
  needs a restart" needs the rules in the core: `RestartRules { io, latency }`
  is the `Loaded::RESTARTS` of §2.2. A plugin's own `Restart`, a `Reload` and a
  `RescanParams(All)` restart on every format. A change that does not restart
  is re-read in place: `ReadLatency`, `ReadTail`, `ReadLayout`. A `TailChanged`
  never restarts.
- **Timers and descriptors** are `TimerId(u32)` and `FdId(i32)`, widths that
  follow the formats' ABIs. A tick runs at most `TIMERS_PER_TICK` and
  `FDS_PER_TICK` (3 each) so the effect bound holds, and the rest stay pending:
  `State::has_backlog` tells the shell to tick again. None is dropped, which
  does not depend on whether a format's timers advance their deadline when
  raised or its descriptors are level-triggered. `MAX_STEP_EFFECTS` (14, the
  busiest tick) is asserted at compile time to fit `EFFECT_CAPACITY`, and `emit`
  asserts rather than drops. A `Callback` makes the tick emit `RunMainThread` alone, because it may
  ask for the rest; the `Replied(Done)` that answers it plans the remainder as
  the tick would have, without running a second callback.
- **A refused rebuild.** `Reply::Refused` to a `Rebuild` leaves the plugin
  `Refused` and remembers it: the next `Activate` or `Reconfigure` rebuilds
  before it activates, since a plugin whose reload failed (VST3) cannot be
  trusted to activate as it is. A refusal clears everything pending, timers and
  descriptors included.
- **Rule 4's "announced" and "stage changed".** A figure is announced when the
  request that raised it was folded into the plan or re-read that produced the
  figure. A layout read notifies `IoChanged` when it differs, or when the
  activation it follows revived a `Refused` plugin; the first layout read of a
  plugin only records it, as the first latency and tail reads do. A `Rebuild`
  that fails is a `Refused`, as a failed activation is.

**Rules.** Written as the table tests will read them.

1. `Op(Activate)` in `Loaded` or `Refused` emits `CallActivate`; in `Active` it
   emits nothing; in `Poisoned` nothing. `Reconfigure` in `Active` emits
   `Recall`, `CallDeactivate`, `CallActivate`; in `Loaded` or `Refused` it is
   `Activate`.
2. `Replied(Activated)` moves to `Active` and emits `ReadLatency`, `ReadTail`,
   `ReadLayout`, then `Lend`. The reads precede the lend, so a format whose
   latency read is not legal during processing (VST3) never sees one.
3. `Replied(Refused)` moves to `Refused { rate }` and emits
   `Notify(Refused)`. No read follows. A later `Activate` or `Reconfigure`
   retries.
4. `Replied(Latency(s))`: `Notify(LatencyChanged(s))` iff `s` differs from the
   stored figure or the plugin announced it, and the first read after load only
   records it. `Tail` likewise. `Layout`: `Notify(IoChanged)` iff the layout
   differs, or the stage changed across the sequence that produced it.
5. `Request(..)` only sets a pending bit. `Tick` plans: `Reload` subsumes every
   other pending request; otherwise any of `Restart`, `IoChanged` and
   `LatencyChanged` (each only where the format's rules say it needs a
   restart, §2.2) and `RescanParams(All)` collapse into one `Recall`,
   `CallDeactivate`, `CallActivate`; `Callback` emits `RunMainThread` first, because it may
   ask for the rest; `RescanParams(Info | All)` reads after the activation, a
   `Values` or `Text` rescan emits `Notify(ParamValuesChanged)` and no restart.
6. A request raised *during* a `CallActivate` is delivered before that effect's
   `Replied`. A `LatencyChanged` or `TailChanged` is accepted only while
   `Active`, so one raised while the plugin activates is dropped and one raised
   before the deactivation is answered when the deactivation completes (rule 9):
   the reads in rule 2 answer both.
7. A request on a `Loaded`, `Refused` or `Poisoned` plugin is consumed and
   changes nothing, except `Callback`, `Timer` and `Fd` on `Loaded`, which run. On
   `Refused` the `Callback` is dropped with the rest.
8. `Died`, from any stage, moves to `Poisoned`, which absorbs every later event,
   and drops a parked plan.
9. A plan that deactivates or rebuilds an `Active` plugin begins with `Recall`.
   `Replied(Returned)` continues the plan. `Replied(Lent)` parks the rest of it in
   `State`, which then emits nothing for the plan until `Event::Returned`, which
   emits the parked tail. Meanwhile `Reconfigure(p)` replaces the parked
   `Prepare`, `Deactivate` replaces the tail with `CallDeactivate`, and a request
   only sets its bit; `Tick` plans just the effects the Controller can run
   (`RunMainThread`, `RunTimer`, `ServiceFd`, reads) and leaves the bits that need a
   restart pending. The plan is the restart: when `Replied(Deactivated)` comes
   the pending `Restart`, `IoChanged`, `LatencyChanged`, `TailChanged` and
   `RescanParams(All)` are answered by the activation and its reads, an `All`
   adding a parameter re-read, and a `Reload` joins the plan as a `Rebuild`, so
   the `Tick` after the return plans nothing a second time. A `RescanParams(All)`
   or `Reload` that finds no activation to follow (a `Deactivate` plan) is kept:
   the next activation reads the parameters.
   The host's latest *intent*, a final stage and `Prepare`, wins: `Reconfigure(p)`
   asks for an active plugin at `p`, `Deactivate` for a loaded one, and
   `Activate(p)` for an active one at `p` only when the intent is not active
   already, as rule 1 leaves an active plugin as it is. So `Activate(p)` on a
   plan that ends active changes nothing, and on one that ends loaded
   (a parked `Deactivate`) adds the activation.
   An op raised while a `CallActivate` is in flight is kept and replayed once the
   activation is answered, `Activated` or `Refused`; a replayed `Reconfigure` or
   `Deactivate` starts with `Recall`. The kept op follows the same intent: a
   `Reconfigure` or `Deactivate` replaces it, an `Activate` never displaces a
   kept `Reconfigure` or `Activate`, and after a kept `Deactivate` becomes a
   `Reconfigure` at its own `Prepare`.
10. `Replied(Stuck)` leaves the plugin `Active`, abandons the rest of the plan,
    emits `Notify(Stuck)` and `Lend`.

11. `Op(LoadState(s))` emits `ApplyLoad(s)` unless the stage is `Active` and
    `shadow_loads` is set (from `Loaded::shadow_loads`, §2.10), in which case it
    emits `LoadShadow(s)` and moves to `SwapPhase::Loading`. A second `LoadState`
    while `Loading` or `Fading` replaces the staged one and emits nothing: the
    latest state wins, and it is loaded once the swap in flight has retired.
12. `Replied(ShadowReady)` emits `SwapTo`, `ReadLatency`, `ReadTail`, and moves to
    `Fading`; the reads answer the swapped-in instance exactly as rule 2 does,
    so a state that changes latency reaches PDC through `Notify`.
    `Replied(ShadowFailed(e))` emits `Notify(LoadFailed)` and returns to `Idle`.
13. `Event::Returned` in `Fading` emits `Retire` and returns to `Idle`, not the
    parked-plan tail of rule 9. A plan raised meanwhile (`Reconfigure`,
    `Deactivate`, a restart bit) parks behind `Retire`, so a rejoin never sees
    two pairs. `Retire` is answered `Done`, then the parked tail runs.
14. `Died` in `Loading` or `Fading` poisons as rule 8 does.

**Properties** (`proptest`, over arbitrary event sequences, no plugin loaded):

- Every `Replied(Activated)` is answered, in the same step, by `ReadLatency`,
  `ReadTail`, `ReadLayout` and then one `Lend`, whatever preceded it. Because the core is
  format-blind, CLAP re-reads both after every activation exactly as the other
  three do.
- `State::renders()` is true only in `Active`. From `Refused` and `Poisoned`
  no sequence of events reaches an effect that renders, and `Refused` is left
  only by an `Activate` or `Reconfigure`.
- A `LatencyChanged` raised inside an activation emits no further
  `CallDeactivate`: the number of `CallActivate` effects over a sequence is at
  most one per `Op` plus one per `Tick` that planned a restart.
- `Reload` subsumes: a `Tick` with `Reload` and any other requests emits
  one `Rebuild` and no bus-cycle.
- No `CallDeactivate` or `Rebuild` on an `Active` plugin is emitted unless a
  `Recall` earlier in the same plan was answered `Returned` or followed by
  `Event::Returned`, and none is emitted between `Replied(Lent)` and `Returned`.
- With `shadow_loads` unset no sequence emits `LoadShadow`, `SwapTo` or
  `Retire`. With it set, every `SwapTo` is followed by exactly one `Retire`, a
  `SwapTo` is never emitted without a `ShadowReady` before it, no
  `CallDeactivate` or `Rebuild` lies between a `SwapTo` and its `Retire`, and the
  `Lend` of rule 2 is never emitted during a swap.
- A parked plan runs once: `Returned` emits it, and a second `Returned` emits
  nothing.
- A restart that ends in `Refused` emits `Notify(Refused)` once and no
  `Notify(LatencyChanged)`.
- `step` is total (no sequence panics), and no step emits more than
  `EFFECT_CAPACITY` effects.
- `Poisoned` absorbs: every later event emits no effect and leaves it
  `Poisoned`.
- The host's latest op wins: with `Reconfigure` and `Deactivate` raised between
  any effect and its reply, the plugin settles in the state the last one asked
  for, with no plan in flight.

`proptest` is a dev-dependency of `tutti-graph` at `1.9.0`;
`tutti-plugin-types` adds the same. The properties run the core through a test
shell that performs each effect against a model of the plugin (split or not,
the Processor held or away) and replies only as a plugin could, so a sequence
is one a real shell could produce; `step_is_total_and_bounded` and the
refused and poisoned properties feed arbitrary events, stray replies included.
The properties are mutation-tested as the testing policy requires, one comment
per test.

### 2.2 The shared traits, static dispatch

In `tutti-plugin-types`, replacing the capability traits and `PluginInstance`.

```rust
/// The control surface, in any state that has a plugin: main thread only.
pub trait Control {
    fn info(&self) -> &PluginDescriptor;
    /// The wiring read from the plugin now, not a load-time cache.
    fn wiring(&self) -> LoadedPlugin;

    fn parameters(&self) -> Vec<ParameterInfo>;
    fn parameter(&self, id: ParamId) -> Option<Normalized>;
    /// Loaded: applied now. Active: an edit queued to the Processor, applied at the
    /// head of its next block (`EditRing`, §2.6).
    fn set_parameter(&mut self, id: ParamId, value: Normalized);
    fn parameter_text(&self, id: ParamId, value: Normalized) -> Option<String> { None }
    fn parameter_value_from_text(&self, id: ParamId, text: &str) -> Option<Normalized> { None }

    fn save_state(&mut self) -> Result<Vec<u8>, PluginError>;
    fn load_state(&mut self, bytes: &[u8]) -> Result<(), PluginError>;

    // Capabilities a format may lack. The defaults say "cannot".
    fn note_ports(&self) -> Option<NotePorts> { None }
    fn editor(&mut self) -> Option<&mut dyn Editor> { None }
    fn presets(&mut self) -> Vec<Preset> { Vec::new() }
    fn load_preset(&mut self, id: &PresetId) -> bool { false }
    fn current_preset(&mut self) -> Option<PresetId> { None }
    fn set_automation_state(&mut self, mode: AutomationMode) {}
    /// Reads parameters again after a rescan the plugin asked for.
    fn rescan_parameters(&mut self, scope: RescanScope) {}

    /// The plugin's own main-thread work (CLAP `on_main_thread`, timers, fds).
    fn run_main_thread(&mut self) {}
    fn run_timer(&mut self, id: TimerId) {}
    fn service_fd(&mut self, id: FdId) {}
}

pub trait Loaded: Control + Sized + Send {
    type Processor: Processor;
    type Controller: Controller<Loaded = Self, Processor = Self::Processor>;

    /// What this format needs a restart for (CLAP: latency and I/O; VST3: I/O
    /// and latency; VST2 and AU: none, they re-read). `RestartRules { io,
    /// latency }`, `State::new`'s argument; a reload restarts on every format.
    const RESTARTS: RestartRules;

    /// Splits the plugin. On failure the whole plugin comes back in the error.
    fn activate(self, prepare: Prepare)
        -> Result<(Self::Processor, Self::Controller), Refused<Self>>;

    /// Rejoins the halves of one activation. A pair from two activations, or a
    /// plugin that will not stop, hands both halves back in `Stuck`.
    fn deactivate(processor: Self::Processor, controller: Self::Controller)
        -> Result<Self, Stuck<Self::Processor, Self::Controller>>;

    /// Rebuilds the instance from its load parameters (VST3 `kReloadComponent`).
    fn rebuild(self) -> Result<Self, Refused<Self>> { Ok(self) }

    /// Whether state loads on this instance go through a shadow (§2.10). `false`
    /// for every format but a VST2 plugin carrying `Vst2Quirks::serialize`.
    fn shadow_loads(&self) -> bool { false }

    /// Loads a second, unactivated instance from the controller's load
    /// parameters (the ones `rebuild` uses). Main thread; may block as a load does.
    fn load_shadow(controller: &Self::Controller) -> Result<Self, PluginError> {
        Err(PluginError::Unsupported)
    }
}

/// The realtime half. `Send` to move to the realtime thread, not `Sync`.
pub trait Processor: Send {
    /// Realtime: no allocation, no lock, no blocking. The only method the audio
    /// thread calls while rendering.
    fn process(&mut self, io: &mut PluginIo<'_>) -> Result<(), PluginError>;

    /// Ends processing (CLAP `stop_processing`, VST3 `setProcessing(false)`, VST2
    /// `effStopProcess`) so the realtime thread can hand the Processor back.
    /// Realtime. Processing starts again lazily in the first `process`.
    fn stop(&mut self);
}

/// The main-thread half. `Send` so the server can build it on one thread and run
/// it on another, not `Sync`, and never used from two threads at once.
pub trait Controller: Control + Send {
    type Loaded: Loaded<Controller = Self, Processor = Self::Processor>;
    type Processor: Processor;

    fn latency(&self) -> Samples;
    fn tail(&self) -> PluginTail;
}

/// An activation that did not take, and the plugin it left.
pub struct Refused<L> {
    /// `None` only where a format cannot hand the plugin back (AU, when both the
    /// activation and its compensating uninitialize fail); `Lifecycle` poisons.
    pub plugin: Option<L>,
    pub reason: PluginError,
}

/// A deactivation that did not take: both halves are as they were.
pub struct Stuck<P, C> {
    pub processor: P,
    pub controller: C,
    pub reason: PluginError,
}

/// One block's buffers, inputs and outputs, in the shape `process` has today.
pub struct PluginIo<'a> {
    pub buffer: AudioBufferMut<'a, 'a>,
    pub ctx: &'a ProcessContext<'a>,
    pub out: &'a mut ProcessOutput,
}

**As built (step 2a).** These details differ from the sketch above.

- `Control` has no `note_ports` or `editor` yet: `NotePorts` and the safe `Editor`
  do not exist before step 5, which adds both to `Control`.
- `Refused`'s `rate` on `Lifecycle::Refused` is an `Option<SampleRate>`: a refused
  *rebuild* has no rate of its own.
- `Layout` is read from `Control::wiring` (`Layout::from(&LoadedPlugin)`), so
  `ReadLayout` has no separate trait method.
- `Lifecycle::Active` has no `swap` field and `Hosted` gains
  `initial_state()` (`State::new(L::RESTARTS)`); step 9 adds the `Swap`.
  `seat` is declared before `controller`, so a dropped `Lifecycle` drops a held
  Processor before the Controller that destroys the plugin (invariant clause 4).
  A lent Processor is not in the enum; the threaded `Hand` (step 8) recalls it
  before the `Lifecycle` is dropped.
- `Control` gains `flush_edits` (default nothing), which `drive` calls on every
  `Tick`: it is the Controller's retry of the parameter edits a full ring
  refused, latest value per parameter (§2.6). It also gains
  `rebuild_midi_mapping`.
- The VST3 restart flags `kMidiCCAssignmentChanged` and `kNoteExpressionChanged`
  are `Request::{MidiCcAssignmentChanged, NoteExpressionChanged}`. A tick turns
  the first into `Effect::RebuildMidiMapping` (after the activation when a
  restart is planned) and the second into `Notice::NoteExpressionChanged`;
  neither restarts. `EFFECT_CAPACITY` and `MAX_STEP_EFFECTS` are 14.
- `drive` does not step `Event::Returned` itself: that is the threaded `Hand`'s
  (step 8). `apply` takes the `hand` and ignores it until then, so both are right
  only for a local hand, whose Processor never leaves the seat and whose `Recall`
  answers `Returned` at once.
- Every call into the plugin that is not a transition (the reads, the main-thread
  work, `flush_edits`) is guarded like one: a panic leaves `Poisoned`, and
  `drive` steps `Event::Died`, so the `State` it owns is never lost to an unwind.
  The host is told: a transition's loss is its `Notice::Refused`, any other
  call's is `Notice::Lost`.
- `flush_edits` runs only on `Event::Tick`, so a host that stops ticking never
  retries an edit a full ring refused. The ticking is the shell's: the loop that
  calls `drive` calls it with `Event::Tick` on every pass.

- `FakePlugin` is `tutti_plugin_types::fake`, behind the `test-support` feature, so
  the server's tests can use it at step 4.

The capability traits of `format_host.rs` stay until step 4: VST2 and AU, and the
server's `Plugin` enum, still use them.

**As built (step 2b, CLAP).** CLAP and VST3 land as two changes; this is the CLAP
one.

- `ClapLoaded` implements `Loaded` and `Control`; `ClapController` implements
  `Control` and `Controller` and does not deref to `ClapLoaded`: the inherent
  surface the format has (editor, state contexts, ports, the `clap-extras`
  extensions) stays reachable while audio runs through `loaded()` and
  `loaded_mut()`, and a call that must also tell the Processor
  (`set_thread_pool`) is a method of the Controller itself.
  The Processor never touches that `ClapLoaded`: it keeps its own copy of the
  plugin pointer, the port layout and the host state, so the Controller's
  `&mut ClapLoaded` has no Rust-level alias. The shell is an `Arc` owning the
  `ClapLoaded`, a `retired` flag and the `processing` flag (distinct from the
  plugin being active; written under the `[audio-thread]` claim). The
  Controller's drop retires the shell, takes the claim, stops processing,
  deactivates and destroys the plugin; the Processor checks `retired` again
  after it takes the claim.
- Two values reach the Processor through `ArcLend` rather than the shell: the
  parameter range table automation and edits are denormalized against (republished
  by `rescan_parameters(Info | All)`, so a rescan that re-describes parameters
  still reaches the audio side) and the `clap.thread-pool` pool
  (`ClapController::set_thread_pool`, which a plain `ClapLoaded` call would not
  tell the Processor about). Both are lent once per block; the Controller
  reclaims them on `flush_edits`.
- The Processor drains the edit ring straight into its input event list, at
  time 0 and before the block's automation, so where both set one parameter at
  one time the automation has the last word. That list is the preallocated
  scratch of §2.6 (no separate merge buffer); it reserves room for as many edits
  as the ring holds (256), which the parameter-point room does not count.
- The plugin's calls into the host raise `RequestWord` bits for `Restart`,
  `IoChanged` (an `audio-ports.rescan` whose flags change a buffer; a names-only
  rescan asks for nothing), `LatencyChanged`, `TailChanged`, `Callback` and each
  `RescanParams` scope. `ClapLoaded::take_requests` is the shell's one pass: it
  takes the word, and turns due timers and ready descriptors into
  `Request::Timer` and `Request::Fd`; `take_raised` is the word alone, for the
  second look after main-thread work that asked for more. A latency or tail
  change raised inside `activate` is answered by the reads after it and is
  dropped there, as the core's rule 4 expects of a request that arrives while
  the plugin is activating (the real shell takes the word only between `drive`s,
  so the host crate drops it).
- The remaining latches (`process_requested`, `params.request_flush`, state
  dirty, note ports, GUI closed) are not in the core's `Request` and stay
  `take_*` flags on `HostState`.
- `load` takes a `LoadOptions` (library path, plugin id) and no rate or block
  size: they are the activation's. `ClapLoaded::sample_rate` and `block_size` are
  placeholders until the first activation. The sample format is `Prepare::format`, a runtime value: `ClapProcessor`
  has no sample type, and `ClapLoaded::negotiate_format` gives the format a
  plugin without 64-bit ports falls back to.
- `set_sample_rate`, `set_max_block_size`, `reactivate`, `needs_restart`,
  `run_main_thread_work` and `ClapError::Deactivated` are gone: a rate change is
  `HostOp::Reconfigure`, and a refused activation leaves the plugin loaded, so
  nothing is "left deactivated" inside an active type. The in-place rollback to
  the previous rate is the bridge's: after a refused `Reconfigure` it activates
  at the previous `Prepare`, and only when that is refused too does the plugin
  stay `Refused` and silent until the next rate. (The session still renders
  nothing after any rate error, because its clock follows the rate the host asked
  for.)
- `PluginIo<'a>` needs one lifetime for the channel tables and their slices
  (`AudioBufferMut<'a, 'a>`), which a caller holding `AudioBufferMut<'t, 'd>`
  cannot produce without copying the tables. `ClapProcessor::render` takes the
  buffer, context and output apart and `Processor::process` is that over a
  `PluginIo`; the server's bridge calls `render` until step 4 settles the
  lifetimes.
- `State::set_mode` records a render mode in the `Prepare` without a restart,
  for a format that applies the mode live (CLAP's `render.set`); the bridge's
  `set_render_mode` uses it, so a toggle does not cycle the plugin and a later
  restart keeps the mode.
- A rejoin does not lose edits: the writes still in the ring and those a full ring
  had refused are flushed into the plugin after it is deactivated
  (`params.flush` is legal when inactive). The bridge settles pending writes the
  same way before a state save or a fork, so they see the writes; a parameter
  flagged `REQUIRES_PROCESS` is not flushed out of band while the plugin is
  processing and stays queued.
- `PluginError::Block(&'static str)` is the error of a failed block: the audio
  thread builds it without allocating (`Process(String)` stays for off-thread
  failures).
- `Notice::Lost` reaches the host as `AsyncEvent::IoChanged` and a log line: the
  wire has no "lost" message, and adding one is a protocol change.
- The server's `ClapInstance` is a bridge: it owns a `Lifecycle<ClapLoaded>`, its
  `State` and a local `Hand`, feeds each pass's requests and a `Tick` to `drive`,
  and turns the notices into the `AsyncEvent`s the `Plugin` enum already
  delivers. It keeps the old capability traits until step 4. What it adds over
  the traits is the same-rate no-op in `set_sample_rate` (the core plans a
  restart for every `Reconfigure`).
- `get_*` getters lose the prefix (`latency_samples`, `tail_samples`,
  `voice_info`, ...; the normalized, typed reads are `Control`'s), the consuming
  `poll_*` latches are `take_*` (N7), `ProcessOutputRef::to_owned` is
  `into_owned` (N4), `resource_get_file_path` and `resource_files_count` are
  `resource_file_path` (a `PathBuf`) and `resource_file_count` (N20), and the
  path arguments are `impl AsRef<Path>` (N19). The `load_*` family is one `load`
  (N14).

**As built (step 2b, VST3).** The second of the two changes. It follows the CLAP
one; what differs is VST3's.

- `Vst3Loaded` implements `Loaded` and `Control`; activating it gives a
  `ProcessorAny` (or `Vst3Processor<T>` through `activate_typed::<T>`) and a
  `Vst3Controller`, which does not deref to `Vst3Loaded` (`loaded()` and
  `loaded_mut()` reach it). `Vst3Active<T>` is gone, with
  `load_with_mode`, `load_class`, `Vst3Active::load`, `set_sample_rate`,
  `restart_bus_configuration` and `activate_with_mode`: `Vst3Loaded::load(path,
  LoadOptions)` takes the class (`LoadOptions::class`) and no rate or block size,
  and the process mode is `Prepare::mode`. A failed `activate` hands the plugin
  back in `Refused`, inactive.
- The Processor holds its own reference to `IAudioProcessor`, the block's
  scratch and a `Reader` of the `IMidiMapping` table, and never touches the
  `Vst3Loaded` the Controller holds. The shell is an `Arc` owning the
  `Vst3Loaded` and nothing else, and has no `retired` flag: the plugin is
  destroyed by whichever half drops last (`Vst3Loaded`'s drop stops processing
  and deactivates first), so a Processor whose Controller went keeps rendering
  against a live plugin instead of racing a teardown, and nothing on the audio
  thread takes a lock for it. `Lifecycle` rejoins the halves before it drops
  either, so on the supported path the last drop is on the control side. A
  Processor that is the last holder (its Controller was dropped first) does not
  tear the plugin down on the thread it renders on: it moves the shell into a
  bounded retirement queue (`Arc::into_inner`, so the check and the release are
  one step), and `Vst3Loaded::reap_retired` destroys what is queued on the
  calling thread; `load`, `activate_typed` and the Controller's `flush_edits`
  tick call it. Only a full queue (64 retired plugins, never reaped) destroys
  in place.
- The threading argument on the shell is stated per call: the Controller runs
  the `IEditController` interface, `IComponent` state and the `[UI-thread &
  Setup Done]` getters (latency, tail) beside `process`, which the SDK permits in
  the `Processing` state (whether `Setup Done` nests, so that those two getters
  are legal while `Activated`, is open: §2.11, U1); the bus arrangement read is
  listed for `Setup Done | Activated | Processing` explicitly. The transitions
  (`setActive`, `setupProcessing`, `setBusArrangements`, `activateBus`) run only
  in the activation and the rejoin.
- A write to the Controller is applied to the edit controller at once
  (`setParamNormalized`) and queued in the edit ring. The Processor drains the
  ring at the head of the block, the latest write to each parameter winning,
  into the first point of that parameter's queue in `inputParameterChanges`
  (`ParameterChangesImpl::prepend_point`), so the block's own automation at the
  same frame has the last word. A plugin whose component is separate from its
  controller hears of a write only that way, which is why the write is queued as
  well as applied.
- VST3 has no `params.flush`, so a rejoin cannot write the ring's leftovers into
  the plugin: they are kept (with the writes a full ring refused, latest per
  parameter) in `Vst3Loaded::carried` and delivered in the first block of the next
  activation. A write on the loaded plugin is recorded there too (it updates the
  controller only, and a separate component hears of a value from
  `IParameterChanges` in a process call, which a loaded plugin does not make), and
  overwrites an entry for the same parameter. A state or preset load drops them
  all, so an older write never goes in over a newer one.
- `save_state` stores `carried` in the blob, because the component's stream does
  not hold those writes. The container is `TUTTIVS3`, a version byte, the
  component length and the two streams; with writes pending it is version 2, which
  puts a `u32` count and that many `u32` id, `f64` value pairs before the length.
  With nothing pending the blob is version 1's, byte for byte. `load_state` reads
  both versions, applies the writes to the controller after the component and
  controller streams (an id the plugin does not list is dropped), and refills
  `carried`; on an active plugin the Controller queues them to the Processor
  instead. A malformed version 2 blob is read as a bare component stream, as a
  malformed version 1 is. A build that predates version 2 reads the whole blob as
  a component stream, so a blob with writes pending does not restore there; only
  tutti reads the container. A blob stores a pending write once per parameter,
  and only for a parameter the plugin lists, so a blob cannot make the next
  activation's first block do more than one point per listed parameter. A v2
  blob whose component stream is empty still restores its writes (and the
  controller's stream) to a plugin whose component has no state.
- A save made while active also stores the writes no block has taken yet. The
  Controller keeps a record of what it handed the Processor (the carried writes
  at activation and every queued edit, latest per parameter, with the ring's
  refusals), and `tutti_rt::drain_clock()` counts the drains the Processor begins:
  the Processor holds the `DrainBeat` (one `begin` per block, before the drain),
  the Controller the `DrainWatch`. After sending a write the Controller takes a
  `DrainMark`; the write leaves the record once `two_since(mark)` is true. Two,
  not one: the drain the mark counted may have read the ring before the write,
  and the next began after the mark was read, so it began after the send and sees
  the write; the one after it began only when that block was over. The fences
  that make this a store-load pair, and `+ 2`, are checked by
  `tutti-rt/tests/drain_clock_loom.rs` against the shipped code (`+ 1` fails it).
  A save in that window is version 2 with the record's writes; a save later is
  the component's stream alone.
- What two drains prove is that the ring was read, not that the plugin took the
  point. Three paths can read a write and not deliver it: the drain overflows
  `pending` (more distinct parameters than its reserve in one drain, reachable
  only by a burst from a plugin with hundreds of parameters; the point is dropped
  and counted in `edits_dropped`), the bus bind fails (only on a sample-width
  mismatch, which a typed Processor cannot have), and `process` fails (the plugin
  was handed the points before it failed, so it is the plugin's loss). Only the
  first is reachable, and a write it drops is in no later save. Fixing it takes
  the Processor publishing its dropped count and the Controller re-sending its
  record entries when the count moves, and a plugin with more parameters than the
  reserve to test it on; neither is done.
- A restored record is applied after the component's stream, so in the two-block
  window a newer value already in the component (automation, or the plugin's own
  edit) is overwritten by the older value of the record. The record holds the
  host's last write to that parameter, and a block later it is gone.
- Two cases stay open. A plugin's own `performEdit` while no block runs reaches
  the host's component handler, and the host records it only if the app relays it
  through `set_parameter`. After a `restartComponent` that changes the parameter
  list, an id left in `carried` is delivered in the first block and the plugin
  ignores it.
- `Control::parameter` answers `None` for an id the plugin does not list
  (`getParamNormalized` answers 0 for it), as CLAP and VST2 do. It finds out by
  walking the parameter list, one COM call per parameter until the match, so a
  caller polling every parameter each frame pays the square of the count. The
  next step is an id set built at load and rebuilt on `kParamTitlesChanged` and
  `kReloadComponent`; it needs interior mutability on `Vst3Loaded` (a `&self`
  read refreshing a cache), which is why it is not in this change.
- `Edit::Reset` (new in the core) says every write queued before it is stale. A
  Controller's `load_state` and `load_preset` send one (CLAP's too), the ring's
  order makes it exact, and a drain applies none of the writes ahead of it. A
  full ring holds the reset for the next tick with every later write behind it,
  so in that case the writes already in the ring still reach one block before it
  lands. The bridge's `settle_edits` before a state save or a fork is
  `flush_edits` only: the write already reached the edit controller, which is
  what the state a save reads belongs to, and a separate component's state lags a
  write by at most a block, which VST3 gives no way to close.
- VST3 has no parameter that requires `process` to be written, so there is no
  `REQUIRES_PROCESS` restriction to respect; no write is held back from the
  controller.
- The `restartComponent` flags are raised as `Request`s on a `RequestWord`
  beside the coalesced flag word that `take_restart` still reads
  (`RestartFlags::raise_into`): `kReloadComponent` is `Reload`, `kIoChanged`
  `IoChanged`, `kLatencyChanged` `LatencyChanged`, `kParamValuesChanged`
  `RescanParams(Values)`, `kParamTitlesChanged` and `kParamIDMappingChanged`
  `RescanParams(Info)`, `kMidiCCAssignmentChanged` and `kNoteExpressionChanged`
  their own, and `kPrefetchableSupportChanged` `Restart`: the SDK says the host
  "has to deactivate the plug-in, calls `getPrefetchableSupport` and reactivate"
  (`ivsteditcontroller.h`), and the old `poll_restart` ran that cycle too. Bus titles, routing and keyswitch changes
  raise nothing, as before. `Vst3Loaded::take_requests` is the shell's one pass.
  A latency change raised inside `activate` is answered by the reads after it and
  dropped there, as the core's rule 4 expects.
- `IMidiMapping`'s table reaches the Processor through an `ArcLend`
  (`Vst3Loaded::rebuild_midi_cc_mapping` publishes, the Processor lends once per
  block), so `Control::rebuild_midi_mapping` takes effect on a live plugin. The
  routing scratch is reserved at activation for a plugin that implements
  `IMidiMapping`, whatever its table holds, because the audio thread cannot
  reserve it when a table first becomes non-empty.
- `Loaded::rebuild` loads the plugin again from its path and class, loads the
  state saved from the old instance into it and drops the old one; a failure
  leaves the old instance in place (`Refused`).
- A render-mode change is a restart here, unlike CLAP's: VST3 delivers the mode
  in `setupProcessing` and the spec forbids calling it while active, so the
  bridge's `set_render_mode` plans a `Reconfigure` at the new mode (not
  `State::set_mode`) and rolls a refusal back to the previous `Prepare`, as a
  refused rate is. The instance, its parameters and its state stay, which the old
  rebuild did too, through a state round trip.
- `Control::presets`, `load_preset` and `current_preset` are the server's
  program-list code moved into the host crate (`Vst3Loaded::program_change_parameter`
  is its public half); `descriptor_of` and the sequencer-context converters moved
  with them. The Controller's `load_preset` goes through its own `set_parameter`.
- `PluginError::Block` is the error of a failed block (`ProcessFailed` is the
  typed processor's): a block the plugin answers with anything but `kResultOk`
  clears the outputs, drops what it emitted and is an error, where it was
  silently empty. An activation's `Vst3Error::PluginError` code reaches the
  server as the text of a `LoadFailed` at the `Activation` stage, not as
  `BridgeError::PluginError`.
- Renames (§2.5): `info` is `plugin_info` (the trait's `Control::info` is the
  catalog descriptor), `read_latency_samples` and `read_tail_samples` are
  `latency_samples` and `tail_samples`, `get_parameter`, `set_parameter`,
  `parameter_string_by_value` and `parameter_value_by_string` are `Control`'s
  `parameter`, `set_parameter`, `parameter_text` and `parameter_value_from_text`,
  `get_parameter_list` is `parameter_list`, `get_state` and `set_state` are
  `Control::save_state` and `load_state`, `set_automation_state(i32)` is
  `apply_automation_state` (the trait's takes an `AutomationMode`),
  `get_factory_info` and `get_class_info` are `factory_info` and `class_info`,
  and path arguments are `impl AsRef<Path>`.
- The server's `Vst3Instance` is a bridge over `Lifecycle<Vst3Loaded>` as
  `ClapInstance` is. The idle pass every dispatch takes (the plugin asked for
  nothing, `State::is_quiet`) does not enter the lifecycle and allocates
  nothing, for both bridges; `drive` takes the state instead of cloning it. A
  pass with work allocates (the core queues its effects), which a restart may.
  The gate is the whole `drain_async_events` of a session, for each bridge.
- A block the plugin fails no longer ends the server: `AudioPipeline::process`
  counts it (`failed_blocks`), clears the MIDI and publishes nothing, so the
  host reads silence and the reply is the usual `AudioProcessed` (the wire has
  no failure flag). This holds for CLAP's errored blocks too, which propagated
  out of `handle` and ended the loop. The log line is the first failure and every
  1024th, on the audio-phase thread.

**As built (step 3, VST2).** The AU half is not in this change (the last bullet);
VST2 is, with `ParamAddress` collapsing to `ParamId`. What differs from the sketch
and from CLAP and VST3:

- `Vst2Loaded` implements `Loaded` and `Control`; activating it gives a `Vst2Processor`
  and a `Vst2Controller`, which does not deref to `Vst2Loaded` (`loaded()` and
  `loaded_mut()` reach it). `Vst2Instance`, `Precision`,

  no rate or block size, and `Vst2Quirks` is step 9's. `RESTARTS` is
  `RestartRules::NONE`: the core reads a changed pin count, latency or tail again.
- The Processor holds a `vst_tutti::RenderHandle` (a copy of the `AEffect` pointer and
  the flags `process` checks, with an `Arc` of the instance's core so `effClose` waits
  for it; `PluginInstance::render_handle`), so the Controller's
  `&mut Vst2Loaded` has no Rust-level alias of anything the Processor calls, and its
  own clone of the plugin's parameter object (`Sync`) for the block's automation. The
  `PluginInfo` it keeps is what the plugin declared at load; the pins, latency and tail
  are read from the plugin when asked (`pins`, `latency_samples`, `tail`, `wiring`).
- The shell is an `Arc` owning the `Vst2Loaded` and an `AtomicBool` for "`effStartProcess`

  after one. It is what makes `effStopProcess` and `effMainsChanged(0)` go once each
  whichever half goes last: a rejoin stops through the Processor and suspends once
  (`resumed`), and a shell dropped with the plugin still processing stops it in its own
  drop. Clause 3 of the invariant is stated as what it is, the host convention, and
  clause 4 is VST3's: a Processor that is the last holder queues the shell for
  `reap`, which `activate` and the Controller's `flush_edits` call.
- An activation sends `effSetSampleRate`, `effSetBlockSize`, `effSetProcessPrecision`

  `effFlagsCanDoubleReplacing`), `effMainsChanged(1)` and `effStartProcess`, in that
  order, and so does a reconfigure after its stop and suspend: a changed rate is no longer
  one opcode but the whole activation. A plugin cannot decline `effMainsChanged`, so
  `Refused` is for what the host can see is no configuration (a rate that is not a
  positive finite number, a block of no frames): the plugin comes back suspended and
  untouched. A request about pins, latency or tail that the plugin raises inside the
  activation is dropped (the reads after it answer it); the rest (a rescan) is kept.
- There is no edit ring for VST2 yet. A write is a direct `setParameter`, which the
  SDK allows from either thread, on the Controller and on the loaded plugin alike, so a
  rejoin has nothing to carry and a state or preset load has nothing to clear
  (`Edit::Reset`). The ring and `Edit::Cheap` arrive with the quirk (step 9), which is
  where VST2 first needs a write to cross to the Processor. A block's automation is
  written at its head, the latest point of each queue, as a host write
  (`host_write`: the plugin's `audioMasterAutomate` echo from inside the call is not
  reported).
- `audioMasterIOChanged` raises `IoChanged`, `LatencyChanged` and `TailChanged` (VST2
  has one notice for all three) and `audioMasterUpdateDisplay` a rescan of the values and
  of the names, on a `RequestWord`; `Vst2Loaded::take_requests` is the shell's one pass.
  The knob moves the plugin reports through `audioMasterAutomate` stay a bounded queue
  (`drain_param_changes`) that the server forwards as `ParameterChanged`.
- The render mode is live: `audioMasterGetCurrentProcessLevel` answers from a flag, so
  `set_offline_render` records it with no restart and the bridge also records it in the
  core's `Prepare` (`State::set_mode`), so a later restart keeps it. A refused rate is
  rolled back to the previous `Prepare` by the bridge, as in VST3.
- `PluginError::Block` is also the error of a block the plugin cannot take: a channel
  slice shorter than the block, or a 32-bit block for a 64-bit activation (a 64-bit
  block for a 32-bit activation is still the narrowing fallback). Neither enters the
  plugin or allocates.
- The server's `Vst2Instance` is a bridge over `Lifecycle<Vst2Loaded>` like the other
  two; its `poll` also forwards the plugin's parameter moves, and the idle pass does not
  enter the lifecycle and allocates nothing (gated through a session's
  `drain_async_events`). `Vst2Instance::probe` reads the identity without activating.
- The in-process node keeps the one lock: a private `Instance` holds both halves under
  it, the audio thread `try_lock`s for the Processor, and a rate change is a rejoin and an
  activation under the lock, on the editor pump as before. The `Instance` keeps the
  render mode in its own `Prepare` (`set_offline_render` records it), so a rate change
  re-activates in the mode the plugin was told, which an export fork relies on. A rate
  the plugin refuses is rolled back, and a plugin that then cannot be activated again is
  lost: its blocks render silence and the pump skips it, with no panic on either thread.
  The graph's `shape` reads the figures the control side last re-read
  (`Instance::figures`) and dispatches nothing. The scratch is the
  Processor's, sized at the activation to the block the plugin was told (a longer
  graph block is split before it reaches the plugin), so the node's own scratch and
  `ensure_scratch_size` are gone.
- `ParamAddress` is `ParamId`: VST2's index is its `ParamId`, converted in
  `tutti-vst2-host` (an id past `i32::MAX` addresses nothing). The wire carries the bare
  `u32`; `PluginControls::indexed` and the node's `address(id, indexed)` are gone, and
  so are the tests of the refusals the mismatch needed (`clap_refuses_a_vst2_index`,
  `add_param_changes_refuses_a_vst2_index`, and the model half of
  `the_addressing_model_survives_the_wire`).
- Renames (§2.5): `get_parameter`, `set_parameter`, `parameter_display` and
  `set_parameter_from_string` are `Control`'s `parameter`, `set_parameter`,
  `parameter_text` and `parameter_value_from_text`; `get_parameter_list` is
  `parameter_list`; `get_parameter_info` is `parameter_info`; `get_state` and `set_state`
  are `save_state` and `load_state`; `latency` is `latency_samples`; `is_resumed` is
  `is_active`; path arguments are `impl AsRef<Path>`.
- **Not in this change: AU.** `AuLoaded`'s `Loaded` and `Control`, the
  `AuProcessor` / `AuController` split, the façade's deletion (with the editor and the
  SysEx assembler moving as §3.4 says), `AuComponentRef` and the borrowed listener, the
  server's `AuInstance` as a bridge, and `tutti-au-host`'s renames. `tutti-au-host`
  cannot be type-checked on a Linux machine: `coreaudio-sys`'s build script needs the
  Apple SDK headers, so none of it builds without macOS, and a change of that size
  written blind is not one to merge unverified. It remains one follow-up. The only AU
  code this change touches is the mechanical `ParamAddress` to `ParamId` edit in the
  server's `loaders/au.rs` and `tutti-plugin`'s `format/gui/au.rs`.

- **The control surface is `Control`, once.** `Loaded` and `Controller` both
  implement it, so `parameters`, `save_state`, `editor` and the rest are declared
  once and a caller reaches them in either state. What an active plugin adds is
  `Controller::latency` and `tail`.
- **`latency` and `tail` stay on the Controller.** No format documents either as
  audio-thread only, and VST3's `getLatencySamples` is `[UI-thread & Setup Done]`,
  CLAP's `latency.get` is `[main-thread & (being-activated | active)]` (the CLAP
  annotation is from the upstream header, which the tree does not carry: §2.11,
  U2). The core
  reads them as effects on the main thread, after `activate` and before `Lend`,
  so a read never overlaps `process` on the formats that restart for latency. The
  Processor carries `process` and `stop` and nothing else: every other read it
  could take would need a per-format argument that the call is legal during
  processing, and none gains from it.
- **`deactivate` is an associated function on `Loaded`.** The result is a `Loaded`
  and the inputs are two values neither of which owns the other; as a method on
  `Controller` it would take the Processor as an argument and make the Controller
  name the lifecycle it otherwise has no part in. On `Loaded`, `activate` and
  `deactivate` sit together, and the check that the halves belong to one activation
  (`Arc::ptr_eq` on the shell, §2.2 soundness) lives beside the code that built the
  pair. A mismatch is `Stuck` with a `PluginError`, never a panic.
- **`Prepare` replaces three things.** CLAP takes its rate and block at `load`,
  VST3 at `activate`, AU in a `StreamConfig`, VST2 at `load`, and
  `set_render_mode` is a deactivate and reactivate bracket in each loader (the
  `PluginAudio::set_render_mode` default is `false`). A change of any `Prepare`
  field is one `deactivate` then one `activate` on any format, which is what
  `HostOp::Reconfigure` plans.
- **The sample format is a runtime choice at activation.** The Processor is the
  half that sees samples. Each host crate's `Processor` for the trait is one
  type that holds the activated `SampleFormat` (`ClapProcessor`) or matches
  `AudioBufferMut::{F32, F64}` to an arm (`ProcessorAny`). CLAP has no typed
  form: its one `ClapProcessor` matches the buffer's width once per block (see
  its runtime-format note). VST3 keeps a typed `Vst3Processor<T>` for a user who
  fixes the sample type at compile time, through an inherent
  `activate_typed::<T>`. The Controller has no sample type: `ClapController`,
  `Vst3Controller`, `Vst2Controller`, `AuController`.
- **Not object-safe, on purpose.** `Loaded`, `Processor` and `Controller` carry
  each other as associated types and the transitions take values. The typestate
  holds a stale handle unnameable; dynamic dispatch would give that up.
- **Each trait states its boundary without "and".** `Control`: what the main
  thread asks of a plugin. `Loaded`: a plugin that is configured but not rendering.
  `Processor`: rendering blocks. `Controller`: the main-thread side of a plugin
  that is rendering.
- **`Refused` hands the plugin back.** VST3 consumes `self` on a failed
  `activate` today (`loaded.rs:392`) and must return it. CLAP returns
  `(Self, ClapError)`, AU `(Option<Self>, AuError)` (`instance.rs:2245`), whose
  `None` is the one case where the unit is still initialized and cannot be
  returned: that is `Refused { plugin: None }`, and `Lifecycle` poisons. A failed
  activation never leaves half a pair: the Processor and Controller exist only on
  `Ok`. `Stuck` is the same for a plugin that will not stop (AU's `uninitialize`
  can refuse, `instance.rs:2322`): both halves return, and the plugin is still
  active.
- **Format-only extras stay inherent**, on `Loaded` or on the Controller as the
  call's thread dictates. `Vst3Loaded::units`, `program_lists`,
  `note_expression_info`; `ClapLoaded::audio_port_info`, `state_with_context`;
  `AuLoaded::load_document_state`; `Vst2Loaded::programs`. A user who wants them
  holds the concrete type.

#### The split reaches one instance: why that is sound

The two halves of an activation reach one plugin instance from two threads. That
is sound only because of the format's own thread rules and the invariant
below. The table names the rule per format; "audio-side" is what the
Processor calls, "main-side" what the Controller calls while the Processor is on
the realtime thread.

| Format | Audio-side | Main-side, concurrent with it | What makes that legal |
|---|---|---|---|
| CLAP | `start_processing`, `process`, `stop_processing`, `reset`, `params.flush` while active (`plugin.h:77-95`, `ext_params.h:303`) | `params.get_value`, `info`, text conversions, `state.save/load`, `gui`, `latency.get`, `tail.get`, `on_main_thread` (`[main-thread]`) | Every entry point carries a thread annotation, `[audio-thread]` or `[main-thread]`, and the two sets are the ones a host calls concurrently. The entries with `active` or `!active` in the annotation (`activate`, `deactivate`) are the rejoin and need both halves. |
| VST3 | `IAudioProcessor::process` (`[processing-thread & Processing]`), `setProcessing` (UI or processing thread) | `IEditController` (`[UI-thread]`), `IComponent::getState/setState` (`[UI-thread & ... Processing]`, `ivstcomponent.h:199-203`), `IUnitInfo`, `IConnectionPoint::notify` | The SDK states the thread of each interface and lists `Processing` as a legal state for the state calls. The component/controller split exists for this: a plugin with a separate controller shares nothing between the two sets but messages, and a single-component plugin that implements both interface sets in one object is bound by the same annotations. Parameter edits do not call across: they reach the processor as `IParameterChanges` in `ProcessData`, from the `EditRing`. `setActive` and `activateBus` are `[UI-thread & Setup Done]` and `setupProcessing` is `[UI-thread & (Initialized \| Connected)]` (`ivstcomponent.h`, `ivstaudioprocessor.h`): they run only in the activation and the rejoin. `getLatencySamples` and `getTailSamples` are `[UI-thread & Setup Done]`; whether that includes `Activated` and `Processing` is open (§2.11, U1), and `Vst3Controller::latency` relies on it. |
| VST2 | `process` / `processReplacing`, `processDoubleReplacing`, the `effStartProcess` / `effStopProcess` pair | The whole dispatcher but the rejoin opcodes: chunks, programs, parameter get, set and display, the editor opcodes | Not the spec: VST2 has none. The host convention (below). |
| AU | `AudioUnitRender`, `MusicDeviceMIDIEvent` from the render thread (`MusicDevice.h:195-200`) | `AudioUnitGetParameter`, `AudioUnitSetParameter`, `AudioUnitGetProperty` / `SetProperty` (class info, latency, tail), the view | `AudioUnitRender` is the one realtime-safe call; parameters are documented as callable from any thread; property access beside render is how AUv2 and AUv3 are hosted (`AUBase` guards properties, never the render path). `AudioUnitInitialize`, `AudioUnitUninitialize` and stream-format changes are the rejoin. |

**VST2 gives no guarantee, and the host does not pretend one.** The SDK says the
dispatcher is called from the UI thread and `process` from the audio thread, that
`setParameter` and `getParameter` may be called from either, and nothing about any
other opcode against `process`. What every major DAW does, and what VST2 plugins
are written and tested against, is the Controller's thread rule: dispatcher calls
on the main thread, concurrent with `process` on the audio thread. That
convention is the de facto contract, not a specified one, and a plugin that
breaks it misbehaves in every host. `Vst2Controller` follows it:

- **Concurrent, the default.** Every dispatcher call runs on the Controller
  beside a running `process`: `effGetChunk` / `effSetChunk`, program get, set and
  name, parameter display and name, `getParameter` / `setParameter`, and the
  editor opcodes. There is no gate, no dropped block and no VST2 case in
  `Processor`, `Controller` or `Lifecycle`.
- **The rejoin.** Only what the plugin cannot take while processing:
  `effSetSampleRate`, `effSetBlockSize`, `effSetProcessPrecision`,
  `effSetSpeakerArrangement` and `effMainsChanged`. They are `Prepare` fields or
  `suspend` / `resume` themselves, so they are `deactivate` then `activate`, with
  the Processor recalled first (rule 9).
- **A per-plugin quirk, off by default** (§2.10). A plugin that races state loads
  against `process` can be marked, by the user or from a known-plugin list; its
  cheap calls then run at the head of a block and its state loads go through a
  shadow instance. The convention stays the default because the quirk costs an
  instance per load and resets the plugin's tails.
- **Rejected: a gate that skips blocks during exclusive calls, and no split for
  VST2.** The first drops audible blocks on every program change; the second makes
  the server's realtime thread special-case one format and grows `Lifecycle` a
  second shape.

**The invariant the unsafe code relies on.** Each host crate has one private
`Shell` per activation, `unsafe impl Sync`, whose `// SAFETY:` says:

1. *One pair.* `activate` creates one `Arc<Shell>` and exactly one Processor and one
   Controller. Neither is `Clone`. `deactivate` consumes both and checks they hold
   the same shell, so no third handle exists and a pair cannot be mixed.
2. *Disjoint entries.* The Processor calls only the audio-side column, the
   Controller only the main-side column. Every method on either takes `&mut self`,
   so each column runs on one thread at a time.
3. *Only concurrent-legal entries run on the Controller while the Processor is
   lent.* Every other entry is the rejoin, reachable only with both halves in
   hand (`Loaded::activate`, `deactivate`, `rebuild`). For VST2 "concurrent-legal"
   is the host convention above, not a rule the format states: that clause is
   argued from what hosts do, and a `Vst2Quirks::serialize` plugin keeps even
   that off the live instance (§2.10). **As built, this clause is held by
   convention, not by the types.** Without `Deref` a Controller still reaches its
   whole `Loaded` through `loaded_mut()`, so a transition-only entry (for CLAP
   `select_audio_port_config`, `apply_audio_port_configuration`, `add_audio_port`,
   `remove_audio_port`, `rescan_audio_ports`) compiles beside a running
   Processor and is refused at run time (`CallError::WrongState`, which the CLAP
   wrappers fold into `false`). §2.11 makes it a compile error.
4. *The plugin is destroyed on the main thread only.* By dropping the `Loaded` that
   `deactivate` returned, or the Controller, whichever ends the shell's use. A
   dropped Processor releases its `Arc` and calls nothing in the plugin. If the
   Controller goes first, its drop marks the shell retired and destroys the
   plugin, and a later `process` returns `Err` without touching it; the Processor
   then frees only the empty shell, which `Lifecycle` avoids by recalling the
   Processor before it drops the Controller.
5. *Callbacks touch atomics only.* A plugin calling the host from either thread
   reaches `RequestWord::raise` and the `EditRing` and nothing else of the shell
   (§2.6).

`unsafe` stays in the host crates: the shell, the FFI calls and the `unsafe impl
Send` and `Sync`, each with a `// SAFETY:` naming the clause above it leans on.
The traits, `Lifecycle` and the pure core add none, and `Handoff` and
`EditRing` carry their own in `tutti-rt` under loom.

### 2.3 `Lifecycle`

```rust
pub enum Lifecycle<L: Loaded> {
    Loaded(L),
    /// The Controller is here; the Processor is held or lent.
    Active { controller: L::Controller, seat: Seat<L::Processor>, swap: Swap<L> },
    /// The plugin refused `rate`; it is loaded, and renders nothing.
    Refused { plugin: L, rate: SampleRate },
    /// A transition failed and left no plugin, or the process died. The shell
    /// sends `Event::Died` for it: the core's `Stage::Poisoned` is reached
    /// only that way.
    Poisoned,
}

pub enum Seat<P> {
    /// On the main thread: single-thread use, between a rejoin and a lend, or
    /// after a recall.
    Held(P),
    /// On the realtime thread, which returns it only between blocks.
    Lent,
}

impl<L: Loaded> Lifecycle<L> {
    /// Interprets one effect against the plugin. Control thread.
    pub fn apply(&mut self, effect: Effect, hand: &mut Hand<L::Processor>) -> Reply;

    /// If the Processor has come back, takes it and steps `Event::Returned`
    /// first. Then `step`, then `apply` every effect it emits, feeding each
    /// `Reply` back, until none remain. `notify` receives the `Notice`s in order.
    pub fn drive(&mut self, state: State, event: Event, hand: &mut Hand<L::Processor>,
                 notify: impl FnMut(Notice)) -> State;

    /// The control surface, in any state that has a plugin, lent or not.
    pub fn control(&mut self) -> Option<&mut dyn Control>;
    /// The Processor, while held. Single-thread users render through this.
    pub fn processor(&mut self) -> Option<&mut L::Processor>;
}
```

`Hand<P>` is the main thread's end of a `Handoff` (§2.6); `Hand::local()` is the
end for a user with no realtime thread, where `Lend` does nothing and `Recall`
answers `Returned` at once. `control` is a borrowed view of the one trait that is
object-safe, not an erased plugin; the typestate stays in the enum.

`apply` is the one place a transition is performed. It takes the plugin out
(`mem::replace(self, Poisoned)`), consumes it through `activate`, `deactivate` or
`rebuild`, and puts back what the result names.

- `CallActivate`: `Ok((p, c))` becomes `Active { controller: c, seat: Held(p) }` and
  `Reply::Activated`; `Err(Refused { plugin: Some(l), reason })` becomes
  `Refused { plugin: l, rate }` and `Reply::Refused(reason)`; `Err` with no plugin
  stays `Poisoned`.
- `CallDeactivate`: needs `seat: Held`. `L::deactivate(p, c)` gives `Loaded(l)` and
  `Reply::Deactivated`, or `Err(Stuck)` restores `Active { Held }` and replies
  `Stuck(reason)`.
- `Lend`: `Held(p)` goes to the hand and the seat becomes `Lent`.
- `Recall`: `Held` replies `Returned`. `Lent` asks the realtime thread for it and
  replies `Lent`.
- `ApplyLoad`: `Control::load_state` on the Controller, in place. `LoadShadow`,
  `SwapTo` and `Retire` move a `Swap<L>` (§2.10): `LoadShadow` fills `Ready`,
  `SwapTo` exchanges the Controllers and lends the shadow's Processor over the
  `Lent` seat, `Retire` runs `L::deactivate` on the old pair and drops it. They
  are never emitted for a plugin whose `shadow_loads` is false.
- A panic out of a transition leaves `Poisoned`, not a half-moved plugin.
- The reads (`ReadLatency`, `ReadTail`, `ReadLayout`) go to the Controller and
  reply `NotActive` when the stage is not `Active`, which is CLAP's rule that
  latency is read only while activated. They are legal with the Processor lent.

**While the Processor is lent**, the plugin is `Active` and rendering, and `drive`
is honest about what it cannot do. The Controller serves the whole control surface
and the reads, `RunMainThread`, timers and fds. Anything that needs the halves
together cannot run: a rate change, a restart, a rebuild. `step` has already
turned each of those into `Recall` first, so `drive` sends the recall and returns
with the rest of the plan parked in `State` (rule 9). It does not wait. A later
`drive` finds the Processor in the hand, sets the seat to `Held`, steps
`Event::Returned`, and the parked tail runs: `CallDeactivate`, `CallActivate`, the
reads, `Lend`. A plan raised in between rewrites the parked tail rather than
queueing a second one.

This replaces `ClapInstance::service_requests`, `note_layout_change`,
`note_latency_change`, `note_tail_change`, `take_changes`, `take_io_changed` and
`Pending`; `Vst3Instance::poll_restart`, `reload` and `RestartChanges`;
`Vst2Instance::poll_changes`; `AuInstance::poll_changes`; the `Meta.loaded`
cache; and `Plugin::poll_async_events`'s per-format arms (fp-edge F1, F10, F11).

#### Why a type, and when (origin: [008](../archive/008-plugin-lifecycle-strategies.md))

**The rule.** A lifecycle boundary is a *type* when crossing it changes what the
object can do and the crossing is rare (VST3, CLAP and AU: `Loaded` and the
active pair). It is a *flag* when the crossing is cheap and frequent. It is
nothing when the ABI has no such state (VST2's `start_process` legality stays
prose). Each format's `Loaded` follows from its ABI, not from taste.

**Adding a fifth format.**

1. Ask what the ABI makes legal only while inactive. If nothing, the format
   gets a flag, not a type.
2. If there is a pre-activation window, make two types and put the boundary
   where the spec's boundary is.
3. A fallible transition returns the receiver in the `Err` (`Refused`, `Stuck`);
   use an `Option` there if backing out can itself fail.
4. Anything switchable on a live instance is a method, not a state.
5. If the plugin holds a pointer into host memory across the transition, pin
   that memory and say so where the pin is.

**The AU pinned pointer.** AU's input render callback holds a `ref_con` into the
instance's render scratch, which is a `Box`. Moving the `Box` moves its pointer,
not its body, so the callback stays valid across the by-value moves of
`activate` and `deactivate`. The `Box` indirection is load-bearing: anything
that frees it must already have run `AudioUnitUninitialize`. VST3 and CLAP have
no such pointer, so their moves are free. Do not flatten it in `AuLoaded`'s
`activate` split.

### 2.6 The shell

A host crate becomes an interpreter of `Effect` over its FFI, and the one place
a plugin's calls into the host enter the core.

**Plugin-initiated calls.** `request_restart`, `latency.changed`, `tail.changed`,
`audio-ports.rescan`, `params.rescan`, `request_callback`
(`clap-host/src/host/state.rs`: `restart_requested`, `latency_changed`,
`tail_changed`, `callback_requested`, `rescan_requested`, `rescan_flags`),
`restartComponent(flags)` (VST3's handler word), `audioMasterIOChanged` (VST2's
host state) and AU's property listener are made on whatever thread the plugin
chooses. Each becomes a bit in one atomic word:

```rust
// tutti-rt: one AtomicU32. `raise` is fetch_or(Release), wait-free, any
// thread; `take` is swap(0, Acquire), main thread only.
pub struct RequestWord(AtomicU32);
impl RequestWord {
    pub fn raise(&self, bit: RequestBit);
    pub fn take(&self) -> RequestBits;
}
```

`RequestBit` is a position in the word, and `tutti-plugin-types` maps `Request`
to one (`Request::bit`, `taken(&word)`); timers and descriptors carry an id and
have none. The `EditRing` is `tutti_rt::edit_ring::<T>(capacity)`, a writer
and a reader end over `Copy` values, and `tutti-plugin-types` types it as
`Edit` with `edits(capacity)` (`EditSink`, `EditDrain`). Both are in
`tutti-rt` as the lock-free rule asks. `RequestWord` is safe atomics; the
ring's slots are `UnsafeCell` words (loom's under the flag, with a `Sync`
argument in `// SAFETY:`), so its model sees each slot's hand-over and checks
the `Release`/`Acquire` on `head` and `tail`. `EditDrain::drain` applies what
was queued when it began, so a hot producer cannot hold the audio thread.

A callback body is `word.raise(..)` and a return value. The main-thread pass
`take`s the word and feeds `Event::Request`s, then `Event::Tick`. Timers and file
descriptors are main-thread registrations (`poll_timers_at`,
`clap-host/src/instance/polling.rs`, already takes `now`): the shell turns a due
timer into `Event::Request(Timer(id))`. `RequestWord` is new lock-free structure
and goes in `tutti-rt` with a loom model beside `pos_ring_loom.rs` that runs
the shipped code (two threads raising while a third takes: no bit lost, each bit
taken exactly once) and a mutation record in it.

**Thread affinity is the token's job** (§2.9, "Thread affinity: the
`MainThread` token"). Every control entry takes a `&MainThread`. The core never
sees a thread. `Lifecycle::drive` and every
`Control` method run on the main thread; `Processor::process` runs on whatever
thread holds the Processor, and it holds nothing else of the plugin.

**Parameter edits.** `Control::set_parameter` on an active plugin pushes an edit
into an `EditRing`, a bounded single-producer single-consumer ring in
`tutti-rt` (new lock-free structure: loom model and mutation record, like
`RequestWord`). The Processor drains it at the head of each block into the
format's own channel: CLAP `PARAM_VALUE` events, VST3 `IParameterChanges`, AU
`AudioUnitSetParameter`, and for a VST2 plugin carrying the quirk `setParameter`.
(A VST2 plugin without it takes `setParameter` on the Controller, which the SDK
allows from either thread, and the drain is idle.) A full ring refuses the edit and counts it; the
Controller keeps the latest value per parameter and retries on its next tick. Nothing on the audio thread allocates or waits.
Apart from VST2 without the quirk, no format's parameter write is called from the
main thread while the Processor runs. The ring's entry is an enum, `Edit::Param`
or `Edit::Cheap(CheapCall)`, a fixed-size `Copy` value, so the quirk's calls
(§2.10) share the ring and its loom model.

**The server's main and realtime threads.** The plugin server renders and
services requests on one thread today. The split is the types' own: the main
thread owns the `Lifecycle`, its `Controller` and the `Hand`, and runs `step`,
`apply` and every control request; the realtime thread owns the Processor, in an
`Option<AnyProcessor>`, and runs the audio request loop, calling only
`Processor::process` and `stop`.

The Processor crosses between them in a `Handoff<P>`, a pair of ends made by
`handoff()`: `Hand<P>` on the main thread, `Rt<P>` on the realtime thread. It is
one slot plus a state word in `tutti-types` (a move into preallocated storage,
`Release`/`Acquire`, no allocation and no lock on either side; loom model and
mutation record).

As built (2026-11, doc 021 step 4a-2): the slot is `tutti_rt::handoff()`, in
`tutti-rt` where the lock-free structure lives, generic over the value and
naming nothing of plugins. `Hand::lend`, `Hand::recall` (a value still on offer
is withdrawn at once), `Hand::take`, and `Rt::poll(last)` between blocks, which
takes an offer or returns the held value on a recall after running `last` (a
Processor's `stop`). A lend into a full slot is refused with its value, so no
misuse can lose or duplicate one. Swap (two Processors through one slot) is
not built: the VST2 shadow it served is not in the graph path. The model is
`tutti-rt/tests/handoff_loom.rs`. `Lifecycle`'s `Hand` joins it with the node
that uses it (step 4a-3).

- **Lend.** `apply(Lend)` moves the Processor into the slot. The realtime loop
  calls `rt.poll(&mut slot)` at the head of each request, between blocks, and
  takes it. Until it does, the plugin renders silence, as a refused plugin does
  today.
- **Recall.** `apply(Recall)` sets the recall flag and posts a `Recall` request
  into the realtime loop's own request queue, so an idle loop (transport stopped,
  no blocks arriving) wakes and sees it. The loop, between blocks, calls
  `Processor::stop` and moves the Processor back through the slot. `drive` does not
  wait: it replies `Lent` and returns. The next `drive` on the main thread finds
  the Processor in the `Hand`, and `Event::Returned` runs the parked plan.
- **No lock is held on the audio thread.** The realtime thread's whole part is a
  few atomic loads and one move per handoff, at a block boundary. The main thread
  never blocks on it either, so a plugin hung inside `process` keeps the main
  thread serving requests, and the server's existing stall detection turns the
  hang into `Event::Died`, which poisons and drops the parked plan.
- **Swap.** A shadow's Processor reaches the realtime thread through the same
  slot while the first is still there (`Lend` with the seat `Lent`); `Rt` sees it
  is holding one and runs both through a fade (§2.10), then returns the old one
  through the slot as a recall does. The slot is one move per direction, so the
  loom model adds one case: an offer taken while a Processor is held, and the
  old one returned exactly once.
- **A rate change or restart** is therefore: `Recall`, the realtime thread returns
  the Processor (one block of latency), `CallDeactivate` rejoins, `CallActivate`
  splits again, the reads run, `Lend`. The client's rate-change reply is sent when
  that plan ends, which its wait loop already tolerates.

Step 8 of §7 is this move; every earlier step runs with `Hand::local()` on one
thread and needs none of it.

### 2.7 Server and client

**Server.** `Session` becomes `Session<P: Hosted>`, with `plugin: Option<P>`, the
`Hand` and the `State` beside it; `Session<AnyPlugin>` is the binary, and
`handle_load` is the only place that needs `AnyPlugin::load`. Its realtime
counterpart is `Render<P: Processor>`, which owns the `Option<P>` and the `Rt`
end. A `FakePlugin` implementing `Loaded`, `Processor` and `Controller`
(`FakeLoaded`, `FakeProcessor`, `FakeController`; records every call, refuses a
chosen rate, can be told to die) runs under `Session<Lifecycle<FakeLoaded>>`.
Both fake halves write a preallocated lock-free call log, so `FakeProcessor` takes
no lock and the no-alloc gate holds on it. This moves rate
refusal then silence then revive, `SetSampleRate`, `handle_process`'s early
returns, the f32 and f64 round trips and the state-chunk path off a real CLAP
plugin and removes the `PLUGIN_LOAD_LOCK` (`lib.rs:635`) from them (fp-edge F7).
The `audio_pipeline` fakes `NanPlugin` and `EchoProbe` become `FakePlugin`
configurations.

The two dedupes ride along: `impl Reaction { fn frames(self) -> impl
Iterator<Item = BridgeMessage> }` for the send loop and `impl From<Notice> for
BridgeMessage` for `drain_async_events` (fp-edge F11).

**Client.** `dispatch.rs`'s `handle` becomes a transition over values:

```rust
pub(super) enum Msg {
    Cmd(Cmd),
    Frame(BridgeMessage),
    Timeout { partial: PartialFrame },
    Eof,
    Tick(Instant),
}
pub(super) fn step(state: ClientState, msg: Msg) -> (ClientState, Cmds);
```

`ClientState` is `Owed`, the partial-frame cursor, the rate-change wait deadline
and the refusal latch. `Cmds` is a small fixed-capacity collection of `Send`,
`Push(AudioResponse)`, `MarkCrashed(cause)` and `LatchRefusal`. The clock is a
value in `Msg::Tick`, the same `_at(now)` seam `poll_timers_at` has. The shell
is the loop that does `ipc::send` and `recv_resumable` and feeds the machine.
`Batcher::await_output` becomes `fn decide(obs: Obs) -> Wait | Done | GiveUp |
Crashed | Refused` with a sleep loop that samples `Obs` (fp-edge F4, F9).

This is the last step because it is protocol-critical and next to the audio
path. It is gated: a no-alloc check over the audio-thread entry points
(`process`, the response `try_recv`) before and after must pass, and where
`Cmds` cannot be shown allocation-free the step does only the rate-change wait
and `decide`.

### 2.9 Safety

- **A safe `Editor`.** (API audit and unsafe audit U2, U3, U14.)

  ```rust
  pub trait Editor {
      fn open(&mut self, parent: raw_window_handle::WindowHandle<'_>, scale: ContentScale)
          -> Result<EditorSize, EditorError>;
      fn close(&mut self);
      // size, hints, resize and idle: the safe forms of today's inherent methods
  }
  ```

  The parameter is `raw_window_handle::WindowHandle<'_>`, not `RawWindowHandle`:
  the latter is safe to forge, the former's constructor is `unsafe` at the caller
  that owns the window, which is the right place for it. No safe trait method
  takes a `*mut c_void`: `HostEditor::open_editor` takes the same handle and the
  `from_ptr` hops (`control_backend.rs:207`, `composite.rs:275`) go. Each format
  extracts the platform pointer inside its own `open`, once. `tutti-plugin-types`'s
  own `WindowHandle` loses `from_raw`, `from_ptr` and `from_u64`; the one
  `unsafe` that decodes the IPC `u64` is in the server, at the single site that
  receives it (`loaders/clap.rs:2535,2571` today). `decode_packet_list_for_test`
  and its twin move behind a `test-support` feature, as `tutti-midi-hardware`
  does.
- **`Send` and `Sync` argued per type.** Each `unsafe impl` carries a `// SAFETY:`
  that says which thread may touch the value and why. `Vst2Instance` loses
  `Sync`: the in-process backend wraps it in a `Mutex`, which needs only `Send`
  (`instance.rs:197`). The same review covers `PluginInterfaces`, `EditorState`
  and the VST3 library handle (`plugin_state.rs:91-92,158-159`,
  `library.rs:80-81`) and `ClapEvent` (`events.rs:95-96`). `BufferPtrs<T>` bounds
  its impls on `T: Sample` and makes its fields private (`BufferPtrs`).
- **The AU safe surface.** `AuComponentInfo.component` becomes an opaque
  `AuComponentRef` that only `component::enumerate*` and `find_component` build,
  so `AuLoaded::new(&AuComponentRef, Prepare)` is safe. `AuParameterListener`,
  `RenderNotify`, `emit_gesture` and `schedule` borrow the `AuLoaded` or
  `AuActive`, which is the "unit outlives listener" proof their `# Safety` text
  asks for. `raw_unit()` is `pub(crate)`. The remaining `pub unsafe fn` count
  reaches zero.
- **Format FFI `unsafe` lives in one crate per format.** A format's host crate
  (`tutti-clap-host`, then `tutti-vst3-host`, `tutti-vst2-host`,
  `tutti-au-host`) is `#![forbid(unsafe_code)]` and holds the logic: the
  lifecycle integration, the shell, the request words, the edit ring's use.
  Everything that touches the format's C ABI is in `tutti-<format>-ffi`, behind
  safe handles over the format's `-sys` crate: the library and its entry, the
  plugin handle with one safe method per extension, the host-side callback
  vtables (each `extern "C"` body under the panic guard, forwarding to a safe
  trait the host implements), the event lists and the process buffers. The FFI
  crate names nothing of tutti's except `tutti-plugin-types` where a value it
  relies on lives there, and carries the `// SAFETY:` argument of every block
  and every `unsafe impl Send`/`Sync`, per type (`undocumented_unsafe_blocks`
  and `missing_safety_doc` are denied in it). The thread rules are in the
  types: a `[main-thread]` entry is a method of the main-thread handle, which
  is `Send` and not `Sync`, and an `[audio-thread]` entry is a method of the
  audio-thread handle, which takes the instance's audio claim for the call, so
  a processor cannot make a main-thread call by construction. The code that
  drives a host crate (the server's loader, the in-process editor) carries no
  format `unsafe` either; its test modules may call into the reference
  plugin's cdylib through `libloading`, which is `unsafe` and cannot go
  through the FFI crate. `scripts/check-plugin-ffi.sh` fails on any `unsafe`
  in those files outside their test modules, and on a missing forbid.
- **Panics do not cross FFI.** Every `extern "C"` and `extern "system"` callback
  body runs under one `guard(|| ..)` per host crate, which returns the format's
  "not handled" value on a panic. With callbacks reduced to `RequestWord::raise`
  and a return value (§2.6), most guards wrap a one-line body; `lock().unwrap()`
  in the callback paths (`host/state.rs:738,761,793`) becomes poison recovery.
- **No raw FFI in public modules.** `tutti-clap-host`'s `host`, `instance`,
  `types` and `topology` are private, its types are re-exported from the root,
  and `as_raw` / `as_raw_mut` are `pub(crate)`. `raw_unit` is `pub(crate)` in
  `tutti-au-host`.

### 2.9a Thread affinity: the `MainThread` token

The main-thread rule was `assert_main_thread`, a `debug_assert!` that did
nothing in release and nothing while no thread was marked. It is now a type.

- `tutti_plugin_types::MainThread` is `!Send` and `!Sync` and `Copy`. Its only
  makers are `MainThread::claim()`, where the first thread to claim becomes the
  process's main thread, a later claim on that thread succeeds again and a claim
  on any other is refused (`NotMainThread`); and `MainThread::current()`, which
  never claims and answers `Some` only on the claiming thread (for a `Drop`,
  which cannot be handed a token).
- The claim is once per process. Under `cargo nextest` a test is a process, so it
  claims freely; under plain `cargo test` the tests of a binary share one.
- An entry that must run on the main thread takes `&MainThread`; holding one is
  the proof and nothing is checked. Converted: all of `Control` but `info`,
  `Controller::{latency, tail}`, `Loaded::{activate, deactivate, rebuild}`,
  `Lifecycle::{apply, drive}` and `Hosted`; `PluginParams`, `PluginState`,
  `PluginPresets`, `PluginEditorHost` and `PluginAudio::{set_sample_rate,
  set_render_mode}`; each host crate's editor, timer, run-loop, state and preset
  methods; `tutti-plugin`'s `HostEditor`, `HostState::load_state` and the
  in-process `PluginEditor`; `Session::{add_plugin, land_reload}`.
- Hosts claim once on their UI thread: `bevy-tutti`'s `TuttiHostingPlugin`
  inserts it as the `NonSend` resource `PluginEditorMainThread`, so Bevy runs a
  system that takes it on the main thread; the plugin server claims in
  `PluginServer::new`.
- AU keeps its OS check (`pthread_main_np`) in `tutti-au-ffi` as well: the
  claimed thread need not be AppKit's.
- A `Drop` has no token. The editor of a dropped `PluginBridge` closes only when
  `MainThread::current()` says so; `ClapLoaded` checks with a
  `debug_assert!` on `MainThread::claimed_elsewhere()` (silent until a host
  claims); the VST2 `PluginInstance` records the thread it was made on and, dropped
  elsewhere, hands its close to the main thread (`tutti_plugin_types::defer_to_main`, run
  by the session's `Phase::Collect`) instead of closing there or skipping it; the CLAP
  `Plugin` does the same with its whole destruction; the VST3
  `Plugin` tears down on the dropping thread. The per-format
  lanes' main-thread handles make that the main thread by construction.
- CLAP, below the host crate: every `Plugin` entry that calls into the plugin
  takes `&MainThread` (`tutti-clap-ffi`), and `ThreadRoles::new(&MainThread)` is
  the one place the main thread is named: `HostState` keeps no second copy, and
  `thread-check`, the `[main-thread]` host callbacks and `Plugin`'s drop read
  it. A `Plugin` dropped on another thread rebuilds itself from its parts (instance, host,
  library) and hands the value to the main thread (`tutti_plugin_types::defer_to_main`,
  run by the session's `Phase::Collect`), which drops it there at its next `run_deferred`;
  the drop is counted (`tutti_clap_ffi::off_thread_drops`, plus a `warn!`) and an `AudioSide`
  still running keeps a valid plugin until then. Only the control-side half defers:
  `AudioSide` holds the core alone and its drop destroys nothing, and a plugin node leaves
  the plan on the control side (`Editor::collect`), so the deferral never runs on an audio
  thread. The `ClapLoaded` `debug_assert!` above is gone. The
  host callbacks CLAP marks `[main-thread]` (timers, descriptors, rescans,
  `mark_dirty`, `latency.changed`, undo, ...) are refused, not forwarded, when
  a plugin calls them from any other thread or from inside an audio claim.
  `deactivate` and `destroy` run under the roles lock without becoming the
  audio thread (`ThreadRoles::claim_lifecycle`; only their `stop_processing`
  is answered as audio-side), so a timer a plugin unregisters from them is
  accepted. `Control::info` has no token, so it measures a CLAP plugin's editor
  on the first ask from the main thread and answers `EditorPresence::Unknown`
  elsewhere.
- CLAP, the rest of the audit's soundness findings. `TaskPool` is an `unsafe
  trait` and `GraphPool::new` takes only a `WorkerPool`, whose gate keeps its
  contract; a wrapped `dyn Pool` is an `unsafe` constructor behind
  `test-support`. `activate` refuses an active plugin and numbers CLAP forbids
  and reads the ports before it calls the plugin; `process` checks the block
  against `[min_frames, max_frames]` and the ports against that layout. A param
  event with a cookie is never lent (the host mints none). State is capped at
  1 GiB and an undo delta at 64 MiB. Output pushes are one at a time (a
  concurrent push is refused, which closes the aliased `&mut` sink). Deferred:
  **S9**, `Bundle::open` is a safe fn that runs native code (the premise of
  loading a plugin, argued at its `unsafe`); **S11**, `thread-check`'s
  `is_audio_thread` answers `false` on a pool helper inside a served task (what
  CLAP requires there is unchecked against the spec); **S12**, the blocking
  claim mutex that `process`, `reset` and `stop` take and the sysex allocation
  in `OutputEventList::push` when its pool is empty (both documented, neither
  memory-unsafe); and the owned domain types for the clap-sys structs in the
  public API (they are pointer-free once the cookie is gone), which go with the
  typed-flags change.
- `Session` paths that free a retired unit (collect, commit, update, drop) take
  no token and check with the same `debug_assert!`; the entries that open an
  in-process plugin (`add_plugin`, `land_reload`) take the token.
- `claim` is first-come and does not ask the OS: the host claims from its UI
  thread at startup, and an AU editor still re-checks `pthread_main_np`.

### 2.10 The VST2 quirk: serialized exclusive calls

`Vst2Quirks`, in `tutti-vst2-host`, is a value on the load path
(`Vst2Loaded::load(path, Vst2Quirks)`), default all off:

```rust
pub struct Vst2Quirks {
    /// Cheap exclusive calls run at the head of a block; state loads and
    /// program changes go through a shadow instance.
    pub serialize: bool,
}
```

The user sets it per plugin, or `Vst2Quirks::known(unique_id)` does from a table
keyed by the plugin's VST2 unique ID. The table ships empty; an entry needs a
reproduction that crashes or corrupts in a host that follows the convention.
`Vst2Loaded::shadow_loads` returns `quirks.serialize`. Nothing else in the
traits, `Lifecycle` or the core names VST2; the core sees a `bool` in `State`.

**Cheap calls: the `EditRing`.** `Edit::Cheap(CheapCall)` carries opcodes whose
whole payload is a scalar or a short fixed string and whose effect is a table
index or a flag, so the plugin has nothing to allocate or wait on:

| Opcode | Why it is cheap |
|---|---|
| `effSetProgramName` | at most `kVstMaxProgNameLen` (24) bytes copied inline into the entry |
| `effBeginSetProgram`, `effEndSetProgram` | no payload; they bracket a program change |
| `effSetBypass` | one int |
| `setParameter` | one float; the ordinary parameter edit |

The Processor makes each call at the head of the next block, before `process`,
from the thread that is already calling into the plugin, so the plugin sees no
concurrency. The list is default-deny: a new opcode is not cheap until it is
argued onto it, and nothing that takes a pointer to a buffer, loads a file or
resizes a table (`effSetChunk`, `effBeginLoadBank`, `effBeginLoadProgram`) is
on it. `effSetProgram` is not either: plugins load samples or allocate on a
program change, so it goes through the shadow like a state load. Opcodes on neither list (editor, display, `effCanDo`) stay concurrent
as in the default. Reads (`getParameter`, `effGetProgram`,
`effGetProgramName`) need a reply and stay on the Controller.

**State loads and program changes: a shadow.** `effSetChunk` (bank and
program) and `effSetProgram` are a `HostOp::LoadState`. Under `shadow_loads`
the core plans it as rules 11 to 14:

1. `LoadShadow(s)`: `apply` calls `L::load_shadow(&controller)`, then
   `load_state(s)` on the new instance while it is `Loaded`, then `activate` at
   the live `Prepare`, and parks the new `(Processor, Controller)` in
   `Active { swap: Swap::Ready { .. } }`. All of it is on the main thread, off the
   audio thread, which keeps rendering the old instance. Any failure drops the
   shadow, replies `ShadowFailed`, and leaves the live pair as it was. A program
   change is staged as the live `effGetChunk` followed by the program index, so
   the shadow starts from the live state.
2. `SwapTo`: `apply` replays the parameter edits made since `LoadShadow` began
   onto the shadow's ring (they are newer than the state), moves the shadow's
   Controller into `controller` and the old one into `Swap::Retiring`, and does
   `Lend` of the shadow's Processor. The seat is `Lent`, so the Handoff slot
   carries a swap. From here `Control` calls reach the new instance.
3. The realtime thread, at the head of the next block, takes the offer,
   crossfades, and returns the old Processor through the slot.
4. `Event::Returned` in `Fading` emits `Retire`: `apply` rejoins the old pair
   with `L::deactivate`, which gives back the old `Loaded`, and drops it on the
   main thread.

```rust
pub enum Swap<L: Loaded> {
    Idle,
    Ready { processor: L::Processor, controller: L::Controller },
    /// Between `SwapTo` and `Retire`: the old half waiting for its Processor.
    Retiring { controller: L::Controller },
}
// Lifecycle::Active { controller, seat, swap: Swap<L> }
```

The swap is an ordinary handoff: `LoadShadow` is `activate` on a second
`Loaded`, `SwapTo` is `Lend`, `Retire` is `deactivate`. No new trait method
beyond `shadow_loads` and `load_shadow` is needed, and both default to refusing.
The quirk is a `bool` the core reads and an `Effect` pair it plans.

**The crossfade.** The graph already has the machinery in `tutti-graph`:
`CrossfadeCurve::gains` (`tutti-graph`'s) and `Fade`. `Graph::crossfade_plugin` in `tutti-session` swaps a
whole `PluginClient`, which means a second server process; it does not reach one
plugin's Processors inside a server, and a swap through it would lose the
node's identity and cost IPC and a process per load. The swap therefore reuses the
curve and not the node-level swap. `Rt`, holding old and new Processors, mixes
`old * g_out + new * g_in` per frame with `CrossfadeCurve::EqualPower` over
5 ms (`Seconds`, converted with `Seconds::to_samples`). Equal power, because the
two instances' tails differ after the reset and sum as independent signals. The
fade table and the old instance's output scratch (`max_block` frames per channel)
are built on the main thread per `Prepare` and ride in the offer, so the audio
thread allocates nothing. A fade longer than a block runs over several; both
Processors receive the block's input and events until it ends, and then only the
new one does.

**Costs.** One extra instance of the plugin exists from `LoadShadow` until
`Retire`: memory, a second `load` (which for a sample-based plugin can take
seconds, on the main thread, with the old instance still sounding), and CPU
for both Processors during the fade. The old instance's internal tails (reverb,
delay lines, filter state, ringing voices) are not carried to the new one; they
fade out within the 5 ms, and the new instance starts from silence. If the new
state reports a different latency the read after `SwapTo` updates PDC through
`Notice::LatencyChanged`, and the fade itself is not latency-aligned.

**`effGetChunk` under the quirk stays on the Controller, concurrent.** Not on the
ring: a chunk's size is the plugin's, `getChunk` commonly allocates and
serializes under locks, and the ring runs on the audio thread. Not from a shadow:
a shadow has only the state it was handed, so it cannot produce the live one.
The remaining race, a torn read against `process`, produces a bad save, not
a crashed host or a corrupted plugin, which is what the quirk exists to prevent.
Rejected: recalling the Processor for the call, which is the dropped-block gate
again.

### 2.11 `Plugin<S>`: the state in the type

The accessor stack is done: #384 (CLAP), #385 (VST3) and #389 (VST2) removed
each Controller's `Deref`/`DerefMut` and reach the `Loaded` through `loaded()` and
`loaded_mut()`, each pinned by a `compile_fail` doctest. That is the first step.
It leaves two things the types do not say, and this section is the second step.

**What the accessor leaves.**

- `loaded_mut()` returns the whole `Loaded`, so a call that is legal only while
  the plugin is inactive compiles on an active Controller and is refused at run
  time. For CLAP these are `select_audio_port_config`,
  `apply_audio_port_configuration`, `add_audio_port` and `remove_audio_port`
  (`CallError::WrongState` in the FFI, folded to `false` by
  `.unwrap_or(false)` in the wrapper, so "wrong state" reads as "the plugin
  declined") and `rescan_audio_ports` (an `Err` while `flags.active`). Invariant
  clause 3 (§2.2) is held by convention until this lands.
- The state is a flag beside the type: `ClapLoaded`'s `LifecycleFlags::active` and
  `Vst3Loaded`'s `Activation` (an `Option<SampleFormat>`, so it also carries the
  width), and `Vst2Loaded::is_active`, which reads the instance's resumed bit.
  `Control::wiring` for VST3 branches on it to decide whether latency is valid
  yet.

**The design.** One handle per format, generic over a sealed stage:

```rust
mod sealed { pub trait Sealed {} }
pub trait Stage: sealed::Sealed {}          // not `State`: §2.1 has one
pub struct Inactive; pub struct Active;     // both sealed

pub struct ClapPlugin<S: Stage> { /* the FFI Plugin, ports, info, .. */ }
pub type ClapLoaded = ClapPlugin<Inactive>;  // every existing name stays

impl<S: Stage> ClapPlugin<S>  { /* parameters, state, port reads, editor: legal in both */ }
impl ClapPlugin<Inactive>     { /* select/apply/add/remove port, rescan, activate */ }
impl ClapPlugin<Active>       { /* latency, tail, presentation latency */ }

pub struct ClapController { plugin: ClapPlugin<Active>, .. }   // no Deref
impl ClapController {
    pub fn plugin(&self) -> &ClapPlugin<Active>;
    pub fn plugin_mut(&mut self) -> &mut ClapPlugin<Active>;
}
```

`Loaded::activate(self, Prepare)` consumes the `Inactive` handle and the
Controller owns the `Active` one; `Loaded::deactivate` consumes both halves and
returns the `Inactive` handle, as today (`Refused` and `Stuck` are unchanged). The
bound is named `Stage` because `tutti_plugin_types::State` is the pure core's.
The aliases keep the call sites: the diff is the `impl` headers, not the 187
`ClapLoaded` references (194 for `Vst3Loaded`, 117 for `Vst2Loaded`; counted). `Control` stays a trait that
both `Plugin<Inactive>` and `Plugin<Active>` implement, so the contract (§6) has
one handle to be generic over; the state-generic `impl` is what it calls.

- **Port configuration only on `Inactive`.** The four CLAP port-config methods and
  `rescan_audio_ports` move to `impl ClapPlugin<Inactive>`; the `Err` and the
  `.unwrap_or(false)` for the active case have no case left to answer. VST3's
  `setBusArrangements` and `activateBus` are `[Setup Done]` and not legal in
  `Activated`: the host sets arrangements before activating, and they too live on
  `Inactive`.
- **Latency and tail only on `Active`.** `Vst3Loaded::latency_samples` is public
  and documented "call this at load time", but `getLatencySamples` is
  `[UI-thread & Setup Done]` (`ivstaudioprocessor.h`) and `setupProcessing` runs
  only inside `activate` (`instance.rs`, the one call site), so on a fresh load the
  call is outside `Setup Done`; `Control::wiring` already reports 0 until active.
  It moves to `Plugin<Active>`, where `Setup Done` holds, and the doc line goes.
  `setAudioPresentationLatencySamples` is `[Activated]` and moves there too.
  `Controller::latency` and `tail` read through `plugin()`.
- **The `active` flags go.** The type is the flag. `Activation`'s width moves
  into `Vst3Plugin<Active>` as a field (it is data, not a flag). The FFI crate's
  shared `Core` keeps its atomic `active` and its run-time `WrongState`: both
  halves reach it through an `Arc`, so it stays the backstop beneath the typed
  handles.
- **VST3's six states stay a run-time matter inside the format crate.** The SDK
  has `Created`, `Initialized`, `Connected`, `Setup Done`, `Activated` and
  `Processing`; this design has two types. `Plugin<Inactive>` covers
  `Initialized`, `Connected` and `Setup Done`, and `activate` runs
  `setupProcessing` before `setActive(1)`. A fresh `Vst3Loaded` is in
  `Initialized`/`Connected`, not `Setup Done` (nothing before `activate` calls
  `setupProcessing`). `Processing` is the Processor's lazy `setProcessing(1)`
  and not a type: it is `Activated` to the Controller. §2.2's "two states" are
  therefore `Inactive` and `Active`, with the six as the format's own detail.
- **VST2 has no spec states.** `Inactive` and `Active` are `effMainsChanged(0/1)`
  by convention (§2.2). `Vst2Loaded::is_active` becomes unnecessary.
- **AU is born in this shape.** `AuInstance` has no `Loaded` yet (step 3), so
  `AuPlugin<S>` costs nothing extra if this lands first. AU's init/uninit rules
  are unread by this design (see the end of this section).

**Why this avoids the VST3 forwarding layer.** Removing the `Deref` leaves the
Controller with a choice for each of `Vst3Loaded`'s public methods (61 `pub fn` in
`host/loaded/`): write a forwarder on the Controller, or
expose the `Loaded`. The plan's forwarding layer was the first, about 90 methods,
every one a copy whose legality in `Active` is again a run-time matter. The
accessor stack took the second and exposes too much. A handle generic over the
stage exposes exactly the right part without a forwarder: the methods legal in
both stages are one `impl<S: Stage>`, and `plugin()`/`plugin_mut()` hand out
`Plugin<Active>`, whose inherent surface is that `impl` plus the `Active`-only
one. The cost is marker types, an alias and moved `impl` headers: the inherent `impl`
blocks to split are 11 (`ClapLoaded`), 7 (`Vst3Loaded`) and 7 (`Vst2Loaded`).

**The doctests it carries.** Four `compile_fail` blocks, each shown to fail for the
stated reason by a mutation (a `compile_fail` block passes on any error, so the
code is pinned by the error: `E0599` for a missing method, `E0382` for a use
after move):

```rust
/// ```compile_fail,E0599
/// controller.plugin_mut().select_audio_port_config(&main, 1);   // Inactive only
/// ```
/// ```compile_fail,E0599
/// loaded.latency(&main);                                        // Active only
/// ```
/// ```compile_fail,E0599
/// loaded.process(&mut io);              // a loaded plugin has no `process`
/// ```
/// ```compile_fail,E0382
/// let _ = loaded.activate(&main, prepare);
/// loaded.select_audio_port_config(&main, 0);   // activate consumed it
/// ```
```

Mutations to record on each: move the port-config methods into
`impl<S: Stage>` and the first fails; move `latency` into it and the second
fails; give `ClapPlugin<Inactive>` a `process` and the third fails; make `activate`
take `&mut self` and the fourth fails. The prototype, kept outside the tree, ran
all four, and its first draft of the first block called `plugin()` (a `&`
borrow), so it failed for the borrow and not the stage; the mutation caught it and
the block uses `plugin_mut()`. The existing three `compile_fail` blocks that pin
"no `Deref`" stay. A zero block or a NaN rate is not a `Prepare` is a run-time
test, not a doctest.

**What types cannot reach.** These stay runtime, checked and tested:

- *Pairing.* A `Processor` of one activation and the Controller of another have
  the same types. `deactivate` checks the activation identity (`Stuck`); the
  contract case `halves_of_two_activations_are_stuck` pins it. A branded lifetime
  cannot work: the Processor is `'static` and moves to the realtime thread.
- *Threads and the `Lent` seat.* Which thread holds the Processor is
  `Lifecycle`'s (`Seat`, `Handoff`), not a type's. `MainThread` (§2.9a) proves the
  main thread; nothing proves the realtime one.
- *Death.* When the process hosting the plugin dies the host-side values are dead:
  `Lifecycle` goes `Poisoned` and the core sends `Event::Died`. No stage applies.
  The client bridge's `running` and `crashed` are two `AtomicBool`s
  (`ipc_client/audio/lifecycle.rs`), a state machine written as flags; whether
  both can be set is traced by no test.
- *A plugin-initiated change.* A plugin never changes the host's stage; it asks
  (`request_restart`, `request_callback`, `kReloadComponent`) and the host
  performs `deactivate` then `activate` on the main thread, after recalling the
  Processor. Both are typed transitions, so the stage survives it.
- *Where the pattern stops.* It pays where the host alone owns the rule, the value
  moves rather than being shared, and the call is a plain method. It does not
  where the device or the peer can change state underneath (`AudioEngine`, the
  client bridge) or the value lives in an ECS resource (`Session`).

**Unknowns.** The numbers are the source audit's; the tree settles none of them.

| # | Open | Settled by |
|---|---|---|
| U1 | Whether VST3's `[UI-thread & Setup Done]` on `getLatencySamples` and `getTailSamples` includes `Activated` and `Processing`. The header lists states without saying they nest; `getBusArrangement` and the state calls list `Setup Done \| Activated \| Processing` explicitly, which suggests `Setup Done` alone does not. If it does not, `Vst3Controller::latency` is a read outside its stated state while `process` runs. | The SDK's state diagram (developer documentation, not in the repo), or Steinberg's validator on a plugin that reads latency while active. If it does not nest, the read moves to the activation's result (cached) or a `kLatencyChanged` restart. |
| U2 | CLAP's `latency.get` annotation, and the other CLAP annotations §2.2 cites (`plugin.h`, `ext_params.h`). `clap-sys` carries none and the C headers are not vendored; `tutti-clap-ffi` repeats some in comments. | Vendor the headers (pinned by SHA, like the VST3 SDK) or read upstream `ext/latency.h`; then re-cite by file. |
| U5 | Whether `flush_params` or `set_plain_value` on an active controller can stall `process`. Both take the `[audio-thread]` claim from the main thread (`ClapLoaded::flush_params`, `set_plain_value`), a mutex that `process` also takes, so the call can block the audio thread for the length of the plugin's flush. Read, not run; no test. | A test with a plugin whose `params.flush` sleeps, timing a concurrent `process`. If it stalls, `flush_params` moves to `Plugin<Inactive>` and an active write goes through the edit ring only. |

Also open: AU's init/uninit rules against this shape (`tutti-au-host` is not
built without macOS), and the compile time of the generic handle (none measured,
none claimed). `Prepare::new` already refuses a rate that is not finite and
positive, and `MaxBlock` a zero block, so that is not open.

## 5. Realtime constraints

- `Processor::process` and `Processor::stop` are the only methods on the audio
  thread, and the Processor reaches the plugin through nothing else. They allocate
  nothing, take no lock and do not block. A format's `process` may return
  `PluginError` from a failed block; the error is built only on that path.
- `step` and `apply` run between blocks on the main thread and may allocate.
  `Effects` is a bounded `ArrayVec` all the same, so a step cannot grow with its
  input and the bound is a tested property.
- `RequestWord::raise` is a single `fetch_or` and is the whole of a host
  callback's work on the audio thread, where a plugin calls one from inside
  `process`. It never allocates or locks. The `EditRing` drain, the `Handoff` poll
  are atomic loads and exchanges with no retry loop. Under the VST2 quirk the
  drain also makes the cheap calls (§2.10), which are table writes by contract; a
  plugin that blocks in one is a plugin that blocks in `setParameter`, and that
  opcode comes off the list.
- The Processor crosses threads only at a block boundary, by a move through the
  `Handoff`. A swap is two moves, the shadow in and the old one out; the fade runs
  on tables and scratch allocated on the main thread, and the old Processor is
  retired (`deactivate`, drop) on the main thread, never on the audio thread. The main thread never waits for it; the audio thread never waits for
  the main thread. A rejoin (`CallDeactivate`, `Rebuild`) never overlaps a block,
  because it runs only after `Event::Returned`.
- Nothing the audio thread reads is published through the core. If a later step
  needs a published value, it goes through `ArcLend` as CLAUDE.md requires.
- `Prepare` changes only through `Reconfigure`, which deactivates first, so
  `process` never sees a block size or sample format change under it.
- The Processor is never dropped on the audio thread: it goes back through the
  `Handoff` and `deactivate` and `Drop` run in `apply`. The plugin is destroyed
  on the main thread only (§2.2, invariant 4).
- The client transition keeps the payload pool's allocation rule: the audio-path
  entry points are checked by `assert_no_alloc` before and after the change.

- **Properties** over `step` with no plugin (§2.1), in `tutti-plugin-types`,
  mutation-tested. They replace the plugin-bound tests whose subject is
  sequencing: CLAP's `a_latency_changed_inside_activate_is_not_restarted_for`,

  restart-flag cases move to state-table tests. The originals stay until the
  loader that held them is deleted, then are kept only where they test the FFI
  call itself.

  VST2 reference plugins, a real activate and deactivate cycle, a real render, a

  tutti-plugin-server` first.
- **`RequestWord`, `Handoff` and `EditRing`** each have a loom
  model that runs the shipped code and a mutation record (`Handoff`: a Processor
  is never in both slots and never lost, and an offer taken while one is held
  returns the old one exactly once; `EditRing`: an edit is applied once, in
  order); threaded stress tests stay out of miri.
- **The quirk, against a `FakePlugin` configured with it** (`shadow_loads` true,
  `load_shadow` building a second `FakeLoaded` that logs its calls). A
  `load_state` on an active plugin reaches the live `FakeController` zero times
  and the shadow once, before its `activate`; the realtime thread then renders
  through the swap, the live pair's `deactivate` runs once after it, and no block

  as a state load; the cheap calls are seen only between blocks, on the
  Processor's thread.

  shadow and the call log shows no overlap on the live instance.
- **Discovery** classification and parsing are in-memory table tests; the

- **The client transition** is table-driven over `Msg` sequences; the hostile-peer
  suite stays as the socket-level check.
- Golden digests, where a format test needs one, go through

### 6.2 Defect: a reset never reaches a plugin in the plugin-server

> **Fixed (2026-11-10).** `Processor::reset` exists (CLAP `plugin.reset`; VST3
> `setProcessing(false)`, restarted by the next block; VST2 drops the host's
> SysEx reassembly only), the server's `PluginAudio::reset` routes to it (AU:
> `AudioUnitReset`), and `Session::handle` sends `M::Reset` there in order with
> `M::ProcessAudio`. Tests: the contract case `reset_clears_the_delay_line`
> (VST2 is its `Gap`) and `a_reset_reaches_the_plugin_between_two_blocks` in
> the server's session tests, against the CLAP probe's call counts rather than
> a `FakePlugin` (the session is not generic over the plugin). The text below
> is the finding as recorded.

**Finding (verified in the tree).**

- `Session::handle` in `crates/tutti-plugin-server/src/session.rs` answers
  `M::Reset` with `Ok(Reaction::None)`, under a comment that calls it deliberate:
  the host clears its pipeline and never rewinds its sequence, so the server has
  nothing to do. That is right about the pipeline. It reaches the plugin not at
  all.
- No other host message resets DSP state. `M::SetSampleRate` re-activates the
  plugin (the CLAP loader returns early when the rate is unchanged), `M::SetRenderMode` sets the
  mode, `M::ProcessAudio` carries the transport but does not request a reset, and
  the rest are parameters, state, editor and shutdown.
- The client does send it: `PluginClient`'s `Node::reset` (`tutti-plugin/src/host/node/graph_node.rs`)
  calls `bridge.reset_rt()`, which queues `Command::Reset`, sent as
  `HostMessage::Reset` (`ipc_client/audio/dispatch.rs`). So a seek or a transport
  reset reaches the server, which drops it.
- The Processor has nothing to call. `Processor` has `process` and `stop` only.
  `ClapProcessor::reset` exists and is not called outside its own tests; the VST2
  in-process node's `reset` says outright that nothing reaches the plugin ("VST 2.4
  has no opcode that clears DSP state on its own").
- The archived audit recorded it as C-2a (`docs/archive/004-plugin-host-gap-audit.md`):
  then `PluginAudio` had no reset hook; now it is `Processor`, which still has
  none. The format halves are built (`ClapProcessor::reset`), the caller is not.

The effect: a reverb or delay tail, a filter's memory, a voice held through a seek
keeps sounding or bleeds across the jump for every CLAP and VST3 plugin hosted
out of process, which is the default for those formats (doc 021 Q3).

**Proposed fix.**

1. `Processor::reset(&mut self)`, realtime, required. CLAP: `plugin.reset` (it
   is `[audio-thread & active]`, which `Processor` is), zeroing `steady_time` and
   clearing the SysEx reassembler, as `ClapProcessor::reset` does. VST3:
   `setProcessing(false)` then lazily `true` in the next block; the SDK says
   `setProcessing` "could be used to reset some buffers (like Delay line or
   Reverb)" (`ivstaudioprocessor.h`), so it is a request, not a clear, and a
   plugin may ignore it. VST2: no opcode clears state (the node's own comment);
   `reset` clears the host's SysEx reassembler and nothing more, and the case is
   a `Gap`. `FakePlugin` records the call.
2. The server's plugin wrapper (`plugin::Plugin` today, `AnyPlugin` after doc 021
   §10) gains `reset`, and `Session::handle` routes `M::Reset` to it, in order with
   `M::ProcessAudio` on the same loop, so a reset is never reordered against a
   block. The pipeline comment stays true and says the plugin is reset too.
3. The client's `Node::reset` already sends it.

**Tests.**

- *Contract (in process), the I1 case:* `reset_clears_the_delay_line` renders an
  impulse in `Mode::Delay`, calls `Processor::reset`, renders silence for
  longer than `spec::LATENCY`, and requires that the impulse never comes out.
  The oracle is the spec's own 137-sample delay, so it needs no comparison with
  another render. Mutation: make `reset` a no-op and the impulse is heard. The
  plugin's cores learn to clear their delay line on `reset`. Expected `Gap`:
  VST2.
- *Server level (the regression):* the same sequence through
  `Session<Lifecycle<_>>` with a `FakePlugin` that records calls: send
  `ProcessAudio`, `Reset`, `ProcessAudio` and assert the call log holds one
  `reset` between the two `process` calls. Mutation: restore
  `M::Reset => Ok(Reaction::None)` and the log shows none.
- The `Reset` row of the session's table test (`("Reset", HostMessage::Reset, Silent)`)
  stays: the reply is still silent.

**Open question: restoring `Realtime` after a failed bounce.** The archive asked
for a guard type so that a bounce failing partway still puts plugins back to
`Realtime`. As built the question is mostly answered, but not by a guard in
`render_mode.rs`: the session owns it (015 §4.3). `Session::export` announces
`Offline` while the export's token lives, `finish_export` drops the token and
announces `Realtime`, and `plugin_render_mode` in `bevy-tutti/src/plugin_host/render_mode.rs`
runs `Phase::RenderMode` every frame as a level, so a despawned
`ExportInFlight` (no `ExportDone`, no `finish_export`) is corrected on the next
frame (`a_despawned_export_restores_realtime`). That system is the safety net and
the token is the guard. What remains open: a headless `Session` caller who never
calls `finish_export` after a failure and runs no `Phase::RenderMode` keeps the
plugins `Offline`; the token's `Drop` could announce, but it is dropped on a
thread that may not be the main thread (015 §4.2 pins the announcement there). The
tree does not decide it. Settled by a headless test that drops the export without
finishing it and reads the mode.

## 9. Crash and hang recovery

Distinct from the `Lifecycle<L>` of §2: that restarts one plugin inside a live
process (re-activation, a rate change). This replaces a plugin whose
`plugin-server` died, or stopped answering. The two meet only at the host
boundary.

**The pure core.** `tutti_session::Recovery::step(RecoveryEvent, now) ->
RecoveryAction` in `tutti-session/src/recovery.rs`: time is a value, there is
no thread and no I/O. Events: died, loaded, load failed, the bridge's block
totals, tick. Actions: wait, terminate, reload (delay, attempt), give up. A
budget of `max_failures` within `window` stops a plugin that crashes on load;
the wait doubles from `backoff` to `backoff_cap`; a reload that never reports
back fails at `load_timeout`.

**The hang verdict.** `PluginHandle::block_counts` reads two monotonic totals
the bridge thread keeps (blocks abandoned on a missed budget, replies taken,
on time or owed): relaxed atomics, nothing on the audio thread. A hang is
abandoned blocks growing with no reply in between, at least `hang_blocks` of
them, held for `hang_window`. A reply, or a stretch of `stall_gap` with no new
abandoned block (a stopped or restarted device sends none), starts the
suspicion over, so a slow plugin that answers is never declared hung and a
frozen count never is. The session then ends the server
(`PluginHandle::terminate`, which latches the reason), so a hung plugin dies by
the ordinary path and is gone before its replacement loads.

**The glue.** The node stays in the graph, silent. The existing `PluginLoad` is
the load, handed to the host as a job (`SessionEvent::PluginReloadDue`) with the
last snapshot as its state; `Session::land_reload` swaps the result in at the
same `AudioNode` (`Graph::replace_plugin`), so every edge is the same edge. A
replacement whose ports differ from the node's is a failed attempt (the edges
would no longer validate). A state that kills the plugin loading it, or that it
dies of soon after (`state_probation`), is withheld from the next attempt
(`StateRestore::Withheld`). The commit re-plans PDC for the replacement's
latency. Modulation lanes on the plugin are rebuilt by the reconciler for the
new unit.

**Limits.** Recovery covers plugins loaded through `Session::add_plugin`, out
of process. An in-process VST2 plugin cannot be recovered (a crash takes the
process) and a hang in it blocks the audio thread, which nothing observes; a
plugin a host inserted itself (`Graph::insert_plugin`, `host_plugin`) has no
recorded path. State changed since the last snapshot is lost. An export
started while the plugin is being replaced is refused (the fork of a dead
plugin cannot save its state).

**As built (the VST2 FFI crate).** The fourth format moved to the rule of §2.9, as a
mechanical split of `vst-tutti` with no behaviour change; the typed handles (§2.9a, the
`Dispatcher`, owned process buffers) are the next change.

- `tutti-vst2-ffi` (layer 4; `tutti-vst2-host` is now layer 5) is the host half of the
  vst-rs fork: the `AEffect` and ABI types, `PluginLoader` and `PluginInstance`, the
  `audioMaster` callback (`callback_wrapper`, under `catch_unwind`, checked by
  `scripts/check-guards.sh`), `HostBuffer`, `RenderHandle`, and from the host crate the
  event buffers (`MidiSendBuffer`, `MidiIo`, `to_midi`) and `RenderScratch`. It keeps the
  `Plugin`, `PluginParameters` and `Editor` traits for the authoring side (nothing in the
  crate implements them since the typed handles); moving them to `tutti-vst2-author` is a
  cleanliness follow-up. MIT, derived from vst-rs 0.3.0 (`LICENSE`).
- `tutti-vst2-host` is `#![forbid(unsafe_code)]`, checked by
  `scripts/check-plugin-ffi.sh`. What its `unsafe` did is a safe API of the FFI crate:
  `PluginEvents` and `SysExMessage` (a view of a plugin's event list that only
  `host_dispatch` can make, handed to the new `Host::process_plugin_events`; the raw `Events`
  keeps its public ABI fields and dereferences nothing),
  `RenderScratch::render_f32_piece` / `render_f64_piece` / `render_f64_as_f32_piece` (stage,
  length-check, render and copy out in one call; the pointer tables are private) and
  `MidiSendBuffer::send_piece` (the pointer tables behind a safe call),
  `PluginInstance` and `RenderHandle` made `Send` (their thread rules are in the next
  entry). The server loader's `unsafe impl Send for Vst2Instance` is gone for the same
  reason, and the typed handles below removed `ControlCell` / `ControlKey`, which only the
  shell's cell needed.
- The plugin-authoring half (`plugin_main!`, `main`, the plugin-side dispatcher,
  `PluginCache`, `util`) is `testing/tutti-vst2-author`, used only by the VST2 test
  plugins; it re-exports the FFI crate's ABI modules, so a plugin names `vst::api` from one
  place. Nothing under `crates/` depends on it.

**As built (the VST2 typed handles).** The live plugin is two handles, and the host crate's
`Shell` is gone.

- `PluginInstance` (the main-thread handle) is the one owner of the plugin and sends
  `effClose` when it drops. Everything that is not a render entry is its method. `RenderHandle`
  (the audio handle) offers `processReplacing`, `processReplacingF64`, `effProcessEvents`,
  `effStartProcess`, `effStopProcess` and `setParameter`, shares the core and never owns the
  plugin: a render handle dropped last closes nothing.
- **Affinity: a token on the entry, not a `!Send` handle.** An entry VST2 puts on the main
  thread takes a `&MainThread` (the proof, as in the other formats): `effOpen`,
  `effMainsChanged`, the sample rate and block size, state, programs, bypass, the editor,
  the MIDI-program queries, `effCanDo`, `effGetTailSize`. A `!Send` handle would not fit
  `Loaded` / `Controller`, which a server builds on one thread and runs on another, and
  `Vst2Loaded` is `Send`; the token is what the other FFI crates already do. A **drop has
  no token**, so the instance records the thread it was made on (under the token it was
  made with) and closes the plugin only there; dropped anywhere else it hands the close to
  the main thread (`defer_to_main`; the session's `Phase::Collect` runs it with
  `run_deferred`, on the claimed thread) and counts it (`off_thread_drops`, plus a `warn!`),
  so a live render handle stays valid until the tick and the plugin is never left open.
  Nothing in the engine's paths drops one off the claimed thread today (an export's fork is
  sent back to the session and dropped by its collect, `poll_exports` is pinned to the main
  thread); the exception is an export still in flight when the world is dropped, which has no
  session left to tick.
- **The gate.** The core holds a mutex the audio entries `try_lock` (never wait) and the
  instance's close `lock`s. After the close every audio entry is refused, to silence for
  `process`, without touching the freed `AEffect`: this replaces S1's "the last handle
  closes" with "the owner closes, and no handle outlives it". It is a `std` mutex, not a new
  lock-free structure (the one uncontended-case cost is a compare-and-swap per audio entry).
- **§2.10 by type, where it is natural.** The exclusive calls (`effSetSampleRate`,
  `effSetBlockSize`, `effSetProcessPrecision`, `effMainsChanged`) hold the same gate for the
  call, so the plugin never sees one beside an audio entry: one in flight finishes first,
  one that starts is refused. The host crate also keeps them to the activation and the
  rejoin. The quirk itself (`Vst2Quirks`, the `EditRing`, the shadow instance) is the next
  change and is not started here.
- **Only `getParameter` and `setParameter` are any-thread in VST2.** They take no token and
  no gate. The dispatcher-based parameter calls (a parameter's name, label and display,
  `effGetParameterProperties`, `effCanBeAutomated`, `effString2Parameter`) must never run
  beside `process`; the in-process backend of `tutti-plugin` calls them off the main thread
  behind its own lock, so they stay token-free as **named exceptions** (with
  `chunk_off_main_thread`) and each holds the audio gate for the call, as the exclusive calls
  do. Narrowing them to the main thread waits for the session to give the backend a route.
- **Poison and the last holder.** A panic under the gate poisons it and marks the core dead:
  later audio entries render silence and never call the plugin again (the instance still
  closes it). A `RenderHandle` that is the last holder of the core (the instance closed first)
  hands the core to the main thread to be freed when dropped off it, so the host box and host
  state never free on an audio thread, whether or not the graph's retire path already keeps a
  unit off it.
- **`HostState::save_state` stays deferred, again with the reason.** `effGetChunk` is a
  main-thread opcode (`PluginInstance::try_get_preset_data` takes the token), but the
  session calls `save_state` from a task-pool job on purpose (a subprocess save is a blocking
  round trip with a ten-second timeout), so the in-process backend has no token. Its one entry,
  `chunk_off_main_thread` / `Vst2Loaded::read_state_off_main_thread`, is the named exception.
  A main-thread route means the session asking the main thread for an in-process plugin's
  state and the pool waiting for the answer: a change to `tutti-session`, `bevy-tutti` and
  the snapshot job's shape, not reasonable inside this change, and a cached snapshot would be
  a behaviour change, not a route.
- The editor is the instance's: `open_editor(&MainThread, WindowHandle)`, `close_editor`,
  `idle_editor`, `editor_size`. `SendEditor` and the `Editor` object it boxed are gone, so
  the editor cannot outlive the plugin or move off it. The server loader's
  `WindowHandle::from_ptr` hop was a no-op re-wrap of the same type and is gone; the
  in-process backend's remains (it takes `HostEditor::open_editor`'s raw pointer).
- The host crate: the Controller **owns** the `Vst2Loaded`; the Processor holds only the
  render handle. `Shell`, `Hold`, the retirement queue and `ControlCell` are deleted, and
  `deactivate` pairs the halves by `RenderHandle::is_of`. The §2.2 invariant's clause 4
  for VST2 reads: the plugin is destroyed by the instance's drop on its own thread, a
  Processor dropped last calls nothing, and a Controller dropped first leaves the Processor
  rendering silence.

**As built (the AU FFI crate).** The third format moved to the rule of §2.9.
It is staged: this change moves the `unsafe` in; the cleanliness pass over the
FFI crate follows as its own change.

- `tutti-au-ffi` (macOS only, empty elsewhere; layer 4, with `tutti-au-host` now
  in layer 5) holds every raw AudioToolbox, CoreAudio, CoreFoundation and Cocoa
  call. `tutti-au-host` is `#![forbid(unsafe_code)]`, checked by
  `scripts/check-plugin-ffi.sh`; every `extern "C"` body in the FFI crate runs
  under `guard`, checked by `scripts/check-guards.sh`.
- Owned handles: `ComponentRef` (a registry component, `Copy`, built only by
  the registry lookups), `Unit` (an `AudioComponentInstance`, disposed when the
  last share goes; `Send`, not `Sync`), `RenderUnit` (the `Send + Sync` share the
  render thread holds). A listener, a render notification, a MIDI output, an
  editor and a renderer each hold a share, so none can outlive its unit. The
  `Plain` sealed trait is the set of types a property can be read into
  (`Unit::get`, `set`, `get_array`).
- `Renderer` owns the heap-pinned scratch the unit's input callback reads and
  withdraws the callback before freeing it; `HostCallbacks` owns the transport
  state the AU pulls and withdraws the callbacks first; `AuParameterListener`
  and `RenderNotify` unregister on drop.
- Public API: `AuComponentInfo.component` is `AuComponentRef` and
  `AuInstance::new`, `new_with_config` and the `AuLoaded` ones are safe and take
  it by value; `raw_unit()` is behind `test-support` and `AuInstance::unit()`
  (a `&Unit`) is what the free functions of `parameters`, `identity` and
  `offline` take; the `pub unsafe fn` count is zero. The raw packet walkers
  moved to `tutti-au-ffi/test-support`.
- Not in this change, as §7 lists them with the `Loaded` impl: the `AuInstance`
  façade stays (its callers are the server loader and the contract; deleting it
  is the `Lifecycle<AuLoaded>` switch), `AuLoaded::new` keeps its explicit rate
  and block size (they come from `Prepare` with the `Loaded` impl), and the
  `AuProcessor` / `AuController` split. The server's and the GUI's `au.rs` keep
  one `WindowHandle::from_raw` each (step 5) and are not in the `check-plugin-ffi`
  scan yet.
- `no_installed_third_party_unit_implements_the_mapping_family` is behind
  `tutti-au-host`'s `installed-units` feature (as `tutti-midi-hardware`'s
  `sequencer-tests`): CI lints it and `cargo xtask test-au-installed` runs it.
- CI lints both AU crates on `macos-latest` (`clippy (macos)`).
- **Known gap: one thread at a time is a convention.** `Unit` is `Clone` and its
  clones share one instance, so nothing in the types stops two clones from
  driving the unit from two threads at once (the handles are `Send`, not `Sync`,
  but a clone is a second handle). The registrations (listener, render notify,
  renderer) need the share to stay alive, which is why it is `Clone`. The
  `Loaded` / `Processor` / `Controller` split closes it: the processor owns the
  render-side handle and the controller the main-thread one, and neither is
  `Clone`. Until then the `AuInstance` facade is the single owner that
  serializes the calls.
- A registration whose withdrawing property write fails (`Renderer`,
  `HostCallbacks`, `AuMidiOutput`) leaks its state instead of freeing memory the
  unit may still read; an editor dropped off the main thread leaks its view.
